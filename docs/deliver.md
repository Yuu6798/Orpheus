# 受け渡しの書き出し（`mv deliver`）

描いた区間の動画をつなぎ、音を付けて元データ（master）にする。元データから、確認用の小さい版と、受け渡しのための片も作る（実験的）。
cv2 を使わないので、fx の extra が無くても動く。描画・送信・公開はしない。

```sh
uv run mv deliver join render_r3 --out render_r3/song_master.mp4 \
    --audio build/src/song.wav --audio-start 132.7 --fade-out 0.5          # seg_<最初>_<終わり>.mp4 のフォルダから
uv run mv deliver join a.mp4 b.mp4 c.mp4 --out master.mp4                  # 区間をこの順に。音なし
uv run mv deliver review-copy render_r3/song_master.mp4 --out song_review.mp4      # 28MB 未満ならそのまま、超えたら 2 パスで約 27MB
uv run mv deliver split render_r3/song_master.mp4 --out upload/master_parts --title "曲名 Shorts r3"   # 25MB の片と結合の bat
```

## つなぎ方（`mv deliver join`）

1. **区間**: 渡した順につなぐ。フォルダを 1 つ渡すと、その中の `seg_*.mp4` を名前の順に使う。
   - 名前が `seg_<最初のコマ>_<終わりのコマ>.mp4`（区間を並べて描くときの名前）なら、区間がすき間なく続くことと、区間ごとのコマ数
     （終わり − 最初）を確かめる。名前が違う区間が混ざっていれば、この確かめは省き、全体のコマ数だけを確かめる。
   - どの区間も、寸法・fps・映像の符号化（codec と画素の形式）がそろっていること。再エンコードせずにつなぐため。
2. **映像**: ffmpeg の concat で、映像を再エンコードせずにつなぐ（`-c copy`）。つないだコマ数が区間の合計と同じかを確かめる。
3. **音**（`--audio` を渡したとき）:
   - `--audio-start` 秒から、映像の長さ（コマ数 / fps）を切り出す。
   - 頭（`--fade-in`、既定 0.02 秒）と終わり（`--fade-out`、既定 0.25 秒）にフェードを掛ける（fx の書き出しと同じ既定値）。
   - AAC 192k・48kHz にする。
4. **元データ**: 映像と音を `-c copy` で合わせ、映像の長さで切り、faststart（先頭に目次）で書く。
   - 既に同じ名前のファイルがあって中身が違えば、`--force` を付けない限り書かない。同じ中身なら `unchanged`。
   - 作業のファイルは出力の隣の一時フォルダに作り、終わったら消す。
5. **記録** `<元データの名前>.deliver.json`（`deliver-join/0.1`、`contracts/` の外）:
   - 区間（パス・sha256・コマ数・名前の区間）と、音（パス・sha256・切り出し・フェード）。
   - 使った ffmpeg（パス・版・sha256）と、ffmpeg のコマンド。
   - 元データの bytes と sha256。
   - 構造検査（寸法・fps・コマ数・音の尺。`technical_pass`。作品の採否ではない）。

色のタグは区間のまま（つなぐだけで変えない）。fx・dance で描いた区間なら BT.709 のまま。

## 確認用の小さい版（`mv deliver review-copy`）

元データをメッセージや携帯で見てもらうための小さい版を作る。作り方は実制作の仕上げと同じ式。

- 元データが `--limit-bytes`（既定 28,000,000 バイト）未満なら、そのまま写す（SSIM は 1）。
- 超えたら 2 パスの H.264 にする。
  - 映像のビットレート = int((`--target-bytes`（既定 27,000,000）× 8 / 長さ − 192k) × 0.985)。192k は音の分で、音はそのまま写す。
  - maxrate 11M・bufsize 22M、preset slow、yuv420p（`--maxrate`・`--bufsize`・`--preset` で変えられる）。色のタグは元データのまま。
  - 元データとの SSIM（ffmpeg の ssim の All）を測って記録する。コマ数が元データと同じかを確かめる。
- **毎回同じバイト列になるか**: x264 を複数のスレッドで動かすと、同じ入力でも走らせるたびにバイト列がわずかに変わる
  （1 パス目の統計から変わる。同じ元データで 3 回作り、3 回とも違った）。
  - 既定の `--threads 1` は、毎回同じバイト列になる。そのかわり 2 パスに時間がかかる（1080×1920・747 コマで約 2 分）。
  - `--threads 0` は ffmpeg に任せる（実制作と同じ。速いが毎回変わる）。記録の `repeatable` に、どちらだったかを残す。
- 記録 `<名前>.review.json`（`deliver-review/0.1`）: 元データ、作り方（写す / 2 パスとビットレート）、設定、ffmpeg とコマンド、
  確認用の bytes と sha256、SSIM、構造検査。中身の違うファイルが既にあれば `--force` が要る。

## 受け渡しの片（`mv deliver split`）

大きな元データを、受け渡しの上限より小さい片に切る。受け取った人は、Windows なら片と一緒に置いた bat で元に戻して確かめる。

- 元データを確かめる: moov が mdat より前（faststart）で、映像の流れがあること。
- `--part-bytes`（既定 25,000,000 バイト）ごとに `<名前>.part00`、`.part01` … に切る（片が 100 を超えると 3 桁）。名前は `--name`（既定は元データの名前）。
  名前は ASCII の英数字と `. _ -` だけ（bat の文字コードと区切りに左右されないように）。
- `join_master.bat`（CP932・CRLF）: `copy /b` で片をつなぎ、`certutil` の SHA-256 を照合して【OK】／【NG】を出す。
  `--title` は bat の見出しの行に入る（既定は名前）。`& | < > ^ % "` と改行、CP932 で書けない字は使えない。
- `<名前の _master より前>_parts_SHA256SUMS.txt`: 片ごとと元データの sha256（`sha256sum -c` で確かめられる形）。
  名前に `_master` が無ければ、拡張子の前の名前を使う。
- 片を順につないだ sha256 が元データと同じかを、その場で確かめる（bat は実行しない）。
- 記録は片のフォルダの隣の `<フォルダの名前>.split.json`（`deliver-split/0.1`）。片のフォルダには受け渡すものだけを置く。
  同じ名前のファイルが既にあれば `--force` が要る。

## 同じバイト列になる条件

手順と ffmpeg の引数は、実制作の仕上げ（片をつないで音を付ける）と同じ。ただし ffmpeg の版が違うと、音の符号化と入れ物の書き方が変わり、
バイト列は変わる。同じ ffmpeg は `ORPHEUS_FFMPEG` で選べる（既定は PATH の ffmpeg、無ければ imageio-ffmpeg 同梱版）。記録の ffmpeg の
sha256 で、同じ ffmpeg だったかを確かめられる。

## 共通の書き出し（`encode.py`）

fx・dance・overlay・timeline・clips の BT.709 の書き出し（`write_video`・`ffmpeg_command`。libx264 / bt709 / tv / yuv420p / AAC）は、
cv2 を使わない `src/mv_pipeline/encode.py` に置いた（`fx/render.py` からも同じ名前で使える）。fx の extra の要らない道具も、同じ書式で書ける。
fx の指紋（`fx.fingerprint`）はこのファイルも含むので、書き出しを変えれば fx の run は描き直しになる。

## 実制作との比較

- 実制作の仕上げの手順（ffmpeg の引数をそのまま写したもの）と、合成の 3 区間（18 コマ）と合成の音で、元データが同じバイト列だった（`tests/test_deliver.py`）。
- 実際の 2 本（縦の Shorts。どちらも 6 区間）でも、実制作が描いた区間と同じ音源から `mv deliver join` で作り直した。どちらも、実制作の記録の
  sha256 とバイト単位で同じだった。

| 本 | コマ | 音の切り出し | フェード | 元データ |
|---|---|---|---|---|
| 1 本目 | 747（24.9 秒） | 132.7 秒から | 0.02 / 0.5 秒 | 63,332,051 バイト、同じ |
| 2 本目 | 837（27.9 秒） | 189.3 秒から | 0.02 / 0.5 秒 | 78,586,291 バイト、同じ |

- **受け渡しの片**: 実制作の受け渡しの道具の書き方（片・bat・SHA256SUMS）をそのまま写したものと、合成の元データで、どのファイルもバイト単位で同じだった。
  実際の 2 本でも、作り直した元データから同じ名前と題名で片を作り、実制作の片・`join_master.bat`・SHA256SUMS のすべてがバイト単位で同じだった。
- **確認用の小さい版**: 実制作の確認用の版は、作り直しても同じバイト列にならない（実制作と同じ書き方を同じ元データで 3 回作り、3 回とも違った）。
  そこで大きさ・コマ数・元データとの SSIM で比べた。
