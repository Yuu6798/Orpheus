# 作品が終わったあと（知見の持ち帰り）

リポジトリの外で作品を作り終えたあと、そこで作った道具と分かったことを Orpheus へ持ち帰る手順。
2 作目と 3 作目の VRM のダンス（どちらもリポジトリの外の制作）で、同じ流れを 2 回通した。それを、作品名を出さない一般の手順にしたもの。

**流れ**: 洗い出し → ユーザーの判断 → 引き継ぎ書と制作後記 → 凍結 → 小さな PR

- 持ち帰るのは、汎用の道具と知見だけ。作品の値（時刻・色・倍率・名前など）・素材・モデル・動画・鍵・費用は持ち込まない（[AGENTS.md](../AGENTS.md)）。
- 範囲・順番・凍結・だれがやるかは、ユーザーが決める。持ち帰る側は、候補と、決めてほしいことを並べる。
- 洗い出し・引き継ぎ書・制作後記は、作った本人が作業フォルダに書く。持ち帰り（PR）は、別の担当がしてよい（2 回とも別のエージェント）。
- リポジトリに入るのは、最後の段の PR だけ。それより前の文書は、どれもリポジトリの外（非公開）に書く。

## 何をどこへ書くか

| 知見の種類 | 何として | どこへ |
|---|---|---|
| Orpheus に既にある部品の使い方・罠 | その部品の節の「N 作目の VRM のダンスで分かったこと」 | `docs/`（公開） |
| 新しく足す部品と、足す理由 | 部品の説明・確かめたこと・限界 | 部品を足す PR の `docs/`（公開） |
| Blender・アドオンの版の違い | 版の違いの箇条 | `docs/model3d.md` の [Blender 5.2 と VRM Add-on](model3d.md#blender-52-と-vrm-add-on)（公開） |
| 見せ方（演出で効いたこと） | その演出の部品の節の知見（例: 分身の節の「縦長の画面は横が狭い」） | `docs/`（公開） |
| 自前の台本で作った所と、引かなかった部品 | 事例 | [自前の描画スクリプトから乗る](external-renderer.md)（公開） |
| 作品の値（時刻・色・倍率・名前・素材の場所） | 照合の台本の中のレシピ・preset | `projects/<作品>/`（Git の外） |
| 照合の結果・持ち帰りの進め方 | 進め方の記録（担当ごとの節） | `projects/<作品>/`（Git の外） |
| 持ち帰りの進み具合 | 1 つの作品に 1 行 | `.claude/memory/STATUS.md`（公開。作品名は書かない） |
| 作業の回し方・反省・ユーザーへのフィードバック | 制作後記 | 作業フォルダ（非公開） |
| 次の作品でも毎回する作業の回し方 | スキル | Git の外（変えるのはユーザーの承認のあと。上げるのもユーザー） |
| 2 回以上踏んだ罠・作業のたびに効く決まり | 決まり | `AGENTS.md`・`CLAUDE.md`（公開。変えるのはユーザーの承認のあと） |
| Orpheus の不具合の種 | 洗い出しの「見つかった問題」→ 直す PR | 非公開 → その部品の PR |
| 確かめていないこと | 限界・未検証 | 部品の節の「限界」、引き継ぎ書 |

公開の側（`docs/`・STATUS・PR の本文）には、作品名・キャラクターの名前・個人のパス・素材・費用・クラウドの保存先の ID を書かない。
作品は「N 作目の VRM のダンス」のように書く（呼び名はユーザーが決める）。

## 1. 洗い出し

ユーザーが完成と言ったら、持ち帰れるものを並べる。この段は「何があるか」まで（順番と PR の計画は、ユーザーの判断のあと）。
置き場は作業フォルダ（非公開）。

- **調べ方**: 作業メモ・道具（先頭の説明）・台本を読み、Orpheus の今の部品（`uv run model3d ops` の一覧と docs）と 1 つずつ照らす。
  Orpheus は最新の main で引く（3 作目の日は、一覧が朝の 54 個から昼の 66 個に増え、作業中のブランチでは 74 個だった）。
- **Orpheus をどこまで使ったか**: 段ごとに、使った部品と回数、使わずに外で書いた所。
- **候補の表**（工程ごと）: 候補・元（作業フォルダの道具）・Orpheus の今・行き先（工程・検査・コマンド・docs）・規模（小・中・大）。
  既にあるので持ち帰らないものも、理由を付けて残す。
- **見つかった問題**: Orpheus の不具合の種（3 作目では、制作の道具で踏んだ「描いてあるコマをとばすと、作り直した後に古いコマが残る」のと
  同じ作りが、Orpheus の続きから描く口にもあった）。
- **逆向きの漏れ**: Orpheus にあったのに引かなかった部品と、その理由（2 回とも見つかった。[先に確かめること](external-renderer.md#先に確かめること)）。
- **非公開のまま・捨てるもの**: 作品の値、素材、一度きりの道具、うまくいかなかった道具。
- **資料に載せる知見**（作品名を除いて公開の側に書けるもの）と、**作成過程の知見**（回し方・反省。制作後記・スキル・決まりへ）。
- **ユーザーに決めてもらうこと**（2.）。

説明文だけで決めた所は「要確認」と書き、引き継ぐ前にコードで確かめる（3 作目では、説明文とコードが食い違う部品があり、確かめ直しで
候補が 34 件から 36 件に変わった）。確かめたのが調べ役の報告なら、そう書く（自分で読んだ所と分ける）。

## 2. ユーザーの判断

洗い出しの最後に、決めてほしいことを番号つきで並べる。返事は、洗い出しの文書に言葉のまま書き写す。決まっていないことは、持ち帰る側が決めずに聞く。

| 決めること | 2 回で決まった例 |
|---|---|
| 範囲 | 全部を持ち帰る |
| まとまりと順番 | 候補を 6〜7 つのまとまりにし、まとまりの順を決める。制作後記と決まりのまとまりは、並べて先に進める |
| 見つかった問題 | 先に別で知らせるか、持ち帰りの中で一緒に直すか |
| 作業フォルダ | 基準として凍結するか（4.） |
| 残す物と片づける物 | 照合に使う物を残し、途中の版はごみ箱へ |
| だれがやるか | 作った本人とは別のエージェント |
| 引き継ぎ書と制作後記 | 両方を書く。「要確認」を確かめ直してから引き継ぎ書を書く |
| 公開の側での呼び名、置き場に迷う候補 | 「N 作目の VRM のダンス」。VRM を受け取る前の確認地点の測りは、3D ツールの検査に置く |

## 3. 引き継ぎ書と制作後記

どちらも作業フォルダ（非公開）に書く。

**引き継ぎ書**（持ち帰る担当が最初に読む入口）:
- 決まっていること（ユーザーの判断と、制作の中で決まったこと）、読む順番、置き場と触ってよいもの。
- 基準（照合の元）のファイルと、その確かめ（4. の作り直しの結果）、確かめていない範囲。
- 動かし方（Blender の版と起動のしかた、外の Python、通しの台本、罠）。
- まとまりごとの渡し方: 汎用の芯、Orpheus に既にある部分（新しく書かずに呼ぶ）、作品の値（非公開。照合の台本に置く）、照合のしかた、罠、前の作品との違い。
- 持ち帰らないもの（既にある部品・使えなかった道具・作品の値）、確かめていないことと分かっている不具合、返事待ち。

**制作後記**（次の作品の参考）:
- 要約、作ったもの、制作の流れ（時刻つき）、新しい試み。
- 振り返り: うまくいったこと、反省点と原因と「次はこうする」、ユーザーへのフィードバック。
- 使い回せる設定値（作品の値。次の作品では測り直す）、次回へのチェックリスト、記録と成果物の置き場所。
- 写しをクラウドにも置くかは、ユーザーが決める。

次の作品では、始める前に制作後記のチェックリストと設定値を読む。値は測り直す。演出は前の作品をまねず、参考にとどめる（3 作目でユーザーが決めた）。

## 4. 凍結

作業フォルダを、照合の基準として凍結する（するかはユーザーが決める。2 回とも凍結した）。

- 凍結の前に、モデルから通しの台本で作り直し、今の基準と同じになるかを確かめる。結果は作業メモと引き継ぎ書に書く（非公開）。
  - 2 作目: 7 段を作り直し、9 つのメッシュの頂点の位置が 7 コマで差 0.0000 mm、布の動きのファイル 2 つが SHA-256 まで同じ。
  - 3 作目: 7 段を作り直し、骨 137 本の姿勢が全コマで差 0、13 コマの変形した後の形も同じ（`check.blend_match` の `exact`）。
  - 作り直していない段は、確かめていない範囲として引き継ぎ書に書く。
- 道具・台本・基準のファイル・完成の動画の SHA-256 と大きさの控えを、作業フォルダの中のファイルに残す（非公開）。そのあとは書き換えない。
- 持ち帰る側は、道具を `projects/<作品>/` へ写してから使い（写しの SHA-256 を控えと比べる）、照合の書き出しも `projects/<作品>/` に置く。
  作業フォルダには書かない。

## 5. 小さな PR

- まとまりごとに担当を分ける（2 回とも、まとまりごとに別のエージェントのセッションを立て、ユーザーとの取り次ぎとマージのお願いは 1 つのセッションがした）。
- 1 つの道具を 1 本の PR にし、合成素材のテストを付ける（まとめて移さない）。試作（凍結した道具）と同じ入力で回して差を数で確かめ、
  PR と docs の「確かめたこと」に書く（`exact`・ビットまで・画素まで・差の平均など）。同じにならない所は、理由（簡易描画の描くたびの揺れなど）を書く。
- 作品の値は、照合の台本の中のレシピに置く。docs には「既定の値は N 作目の VRM のダンスで決めた値」のように書く。
- 見直しの正しい指摘でも、直すと試作との照合が崩れるときは、既定を試作と同じにし、正しい計算をオプションにする（#81・#96・#123・#146）。
- 前の PR のブランチに積んだ PR は、前がマージされてから main の最新に載せ直し、全体のテストを回してから出す。マージはユーザーがする。
- 見直しの指摘はコードで直す。スレッドへの返信と解決は、ユーザーの OK を待つ（2 作目から、こうして進めている）。
- 知見の置き場は、PR を出す前に担当の間で決めておく（同じことを 2 か所に書かないため）。
  - 既にある部品の知見は、その部品の節に書く。
  - 新しく足す部品の知見は、その部品を足す PR が書く。
  - 作業の回し方と反省は、制作後記とスキルへ（スキルはユーザーの承認のあと）。
  - 2 回以上踏んだ罠と、作業のたびに効く決まりは、決まりへ（ユーザーの承認のあと）。
- 進み具合は `.claude/memory/STATUS.md` の 1 行に、まとまりが終わるたびに書き足す。
- 担当は、終わったら進め方の記録（`projects/<作品>/`。非公開）に自分の節を書く: PR の表（中身と照合）、照合の置き場、分かったこと、
  確かめていないこと、返信していない見直しのスレッド。

## 2 回の実例

- 2 作目の VRM のダンス: 候補 34 件を 6 つのまとまり（制作後記と、道具の 5 つ）にし、道具は 33 本の PR（#126〜#171）に分けた。どの道具も凍結した道具と同じ入力で照合した
  （バイト単位・SHA-256・画素まで同じ、または差の大きさ）。docs に書いた知見は、たとえば [揺れものを焼く](model3d.md#揺れものを焼くvrmbake_springs) の
  「揺れものの知見」、[VRM を書き出す](model3d.md#vrm-を書き出すvrmexportと中身を確かめるcheckvrm) の「VRM に入らないもの」。
- 3 作目の VRM のダンス: 確かめ直しの後の候補 36 件を 7 つのまとまりにした（表情・揺れものと動きのつなぎ・カメラ・光と塗り・腕と布・確認地点・
  制作後記と決まり）。

その前（2026-11-06〜）の、リポジトリの外の制作の道具を工程ごとに移す計画（[ロードマップ › ツールキットの計画](roadmap.md#ツールキットの計画2026-11-06)）も、
洗い出しから小さな PR に分けて移した。この文書の手順は、3D の VRM のダンスの 2 回から作った（ほかの種類の制作で、この形のまま通したことはまだ無い）。
