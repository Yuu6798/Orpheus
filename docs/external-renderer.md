# 自前の描画スクリプトから乗る

fx や dance に無い描き方を、自前の Python で書くときの手順。描画そのものは自分のスクリプトで行い、
**色・記録・つなぎ・検査**の決まりだけを借りる。描画スクリプトそのものは、リポジトリに入れない（作品の値を含むため）。

## 先に確かめること

まず、リポジトリの道具が動く状態にする。`uv sync` が「uv が必要な版より古い」と止まったら、README の「必要なもの」のとおり uv を入れ直して続ける
（[README › 必要なもの](../README.md#必要なもの)）。道具が「動かない」ことを理由に、自前で書き始めない
（[事例（2026-11-11）](#事例2026-11-11)では、古い uv を理由に制作の最後まで道具を使わなかった）。

欲しい演出が、もう部品として無いかを見る。初見だと見落としやすい。

| 欲しいもの | ある場所 |
|---|---|
| カメラ・空間レイヤー・局所光・調色（深度とマスクは任意） | fx-shot（[fx](fx.md)） |
| カット・クロスフェード・黒・フラッシュ・焼け抜けでつなぐ | [fx › timeline](fx.md#timeline複数のショットをつなぐfx-timeline02) |
| 炎・刃の火・火の粉・灯の点灯・稲光・雨・暖色の光・煙・形（題字など）に集まる光の粒 | [fx › 演出の hooks](fx.md#演出の-hooks火空と天気明かり)（`fx.fire`・`fx.sky`・`fx.accent`・`fx.particles`） |
| 透過の連番（歌詞・題字）を重ねる。コマ番号のずらし（`first_frame`）・無いコマは透明・影・光彩・色つけも、ここの口で足りる | [fx › overlay](fx.md#overlay透過レイヤーの重ね合わせfx-lyric-1) |
| 緑背景の人物を舞台に合成する | [dance](dance.md) |
| 曲の拍の格子（テンポ・位相・小節の頭） | `mv audio grid`（[audio](audio.md)）。探す範囲（`--bpm-min`・`--bpm-max`）が要る。広く取ると半分のテンポを選ぶことがある |
| 完成動画の画面全体の明滅を数える | `mv gate flashes`（[gate › 完成動画の明滅を測る](gate.md#完成動画の明滅を測るmv-gate-flashes)） |

歌詞付きの制作なら、作る前に `mv workflow plan`（[workflow](workflow.md)）で必要な工程を確かめる。

それでも無ければ自前で描く。そのとき借りるのは次の 5 つ。

| すること | 借りるもの |
|---|---|
| 光や炎を置く位置を読む | `mv fx guides`（[fx › 見比べの補助](fx.md#見比べの補助目盛り基準の列比較動画)） |
| コマを H.264 に書く | `mv_pipeline.encode.write_video`（[deliver › 共通の書き出し](deliver.md#共通の書き出しencodepy)） |
| 描画を run として記録する | `mv fx legacy --units frames`（[fx › legacy 接続](fx.md#legacy-接続)） |
| 区間をつないで音を付ける | `mv deliver join`（[deliver](deliver.md)） |
| コマを並べて見る | `mv sheet`（[sheet](sheet.md)） |

## 書き出しは `write_video` を使う

```python
from mv_pipeline import encode

def frames():                       # RGB の uint8、(高さ, 幅, 3)
    for n in range(first, last):
        yield draw(n)

encode.write_video(out, frames(), (1920, 1080), 30, 17, last - first)
```

`write_video` は、BT.709 の式で YUV にして BT.709 の印を付け、一時名に書いて、ffmpeg が成功し枚数が揃ったときだけ置き換える。
cv2 を使わないので、fx の extra が無くても動く。

**自分で ffmpeg の引数を書かない。** RGB のコマを ffmpeg に既定のまま渡し、出力に BT.709 の印だけを付けると、式は BT.601 のまま、
印だけが BT.709 の動画になる。再生機は印を信じて BT.709 で読むので、色がずれる（[roadmap](roadmap.md) の原則にも同じ注意がある）。

2026-11-10 に、ffmpeg 6.1.1 で、同じ色票（下の見本のコマ。320×180・CRF 18）を 2 通りに書いて測った値
（一方は `bgr24` のコマを libx264 に `yuv420p` で渡し、`-colorspace bt709` などの印だけを付けた。もう一方は `write_video`。どちらも、印に従う既定の読み方で RGB に戻した）:

| 元の色（RGB） | 印だけ付けた動画を読んだ色 | `write_video` で書いた動画を読んだ色 |
|---|---|---|
| 255, 0, 0 | 255, 23, 0 | 254, 0, 0 |
| 0, 255, 0 | 0, 214, 0 | 0, 254, 0 |
| 64, 160, 224 | 53, 154, 226 | 63, 158, 224 |
| 224, 192, 64 | 227, 186, 57 | 223, 190, 64 |

- 実際の絵（1080p の 4 コマ）の彩度の高い画素では、緑が平均で +3.4〜+9.9 ずれていた。書き出しを `write_video` に替えると −0.7〜−1.3 になった。
- 並べれば分かるが、1 本だけを見ても気づかない程度の差。だから測るまで見つからなかった。
- ffmpeg の既定の振る舞いは版で変わる。上の値は 6.1.1 のもので、ほかの版では測っていない。

2026-11-11 の制作で、同じ罠をもう一度踏んだ（測ったのは 2026-11-12）。JPEG の連番を自前の ffmpeg の引数（`pad` と `format=yuv420p`、libx264、
`-colorspace`・`-color_primaries`・`-color_trc` に bt709 の印だけ）で書いた。実際の絵の 9 コマ（ffmpeg 6.1.1）で、印に従って読んだ動画と
元の JPEG を比べた（動画 − 元の符号つき平均の差。単位は 0〜255 の値）。印だけ付けた方は CRF 26。同じコマを `write_video`（CRF 23）で書き直して音を `-c:v copy` で付けたものも比べた:

| 画素 | 印だけ付けた動画（R・G・B） | `write_video` で書き直した動画（R・G・B） |
|---|---|---|
| 全部 | +0.58・+1.17・−0.21 | −0.65・−1.09・−0.56 |
| 彩度の高い画素（最大 − 最小 ≥ 80。39.3 万画素） | +3.26・+6.79・−0.60 | −2.23・−0.97・−0.49 |
| 強い赤（1.7 万画素） | −1.71・+7.76・+2.10 | −7.34・+0.26・+2.11 |
| 紫（26.6 万画素） | +0.70・+8.48・−0.89 | −2.74・−0.63・−2.57 |

- 緑のずれは消えた。残った差は、強い赤の画素の R が −7.3（コマごとに −5〜−12）。その画素は少なく、多くは細い線。原因は調べていない
  （4:2:0 の色の間引きは推測で、確かめていない）。
- 上の注意は、このとき既にこのページにあった。エージェントはこのページを読まずに描画スクリプトを書いた。[AGENTS.md](../AGENTS.md) がここを指すようにしたのは、このため。

## 見本（合成素材）

`examples/external/render_frames.py` は、色票と動く帯を描くだけの小さなレンダラ。引数は `CONFIG seg START END OUT` で、
`mv fx legacy --units frames` が呼ぶ形と同じ（START・END はコマ番号で、END のコマは含まない。END が START 以下なら、描かずに止まる）。

```sh
mkdir -p projects/external-demo
echo '{"width": 320, "height": 180, "fps": 24}' > projects/external-demo/config.json

# 区間を描く（名前は seg_<最初のコマ>_<終わりのコマ>.mp4）
uv run python examples/external/render_frames.py projects/external-demo/config.json seg 0 48 projects/external-demo/segs/seg_0000_0048.mp4
uv run python examples/external/render_frames.py projects/external-demo/config.json seg 48 96 projects/external-demo/segs/seg_0048_0096.mp4

# つなぐ（区間が続いていることとコマ数を確かめ、sha256 と ffmpeg の版を記録する）
uv run mv deliver join projects/external-demo/segs --out projects/external-demo/master.mp4

# 並べて見る
uv run mv sheet projects/external-demo/master.mp4 --out projects/external-demo/sheet.png --at 0.5 1.5 2.5 3.5

# 描画を run として記録したいとき（renderer と config の sha256、argv、終了コード、所要時間が残る）
uv run mv fx legacy --renderer examples/external/render_frames.py --config projects/external-demo/config.json \
    --start 0 --duration 2 --units frames --fps 24 --width 320 --height 180 --out projects/external-demo/fx_runs
```

リポジトリのルートで実行する。出力はどれも `projects/external-demo/` の下にできる（`projects/` は `.gitignore` 済みなので、Git に入らない）。

`tests/test_external_renderer.py` が、この見本で legacy・join・色の読み戻しと、空の区間で止まることを確かめる。

## 描画スクリプトの作り

- **コマ番号だけで絵が決まるようにする。** 前のコマの状態を持たない。区間を並べて描けて、直した区間だけを描き直せる。
  粒や炎も、時刻から位置を計算する（hooks の部品と同じ作り）。
- **区間の名前は `seg_<最初>_<終わり>.mp4`。** `mv deliver join` が、区間がすき間なく続くことと、区間ごとのコマ数を確かめる。
- **位置は素材の正規化座標で持つ。** カメラの変換で画面へ写す。カメラが動いても、光や炎が絵の同じ所に付く
  （hooks の `view.point` と同じ考え方。fx の光の座標の決まりとも同じ）。
- **歌詞・題字は絵と別の透過の連番にする。** 絵を描き直さずに歌詞の案を差し替えられる。土台と同じ寸法・曲全体のコマ番号で描くと、
  `mv overlay --layers` の `first_frame` でそのまま重なる。寸法が違うと重ねられない（`mv overlay` は寸法の一致を求め、縮尺は縦横比 1% 以内だけ。
  位置をずらす欄は無い。2026-11-11 は連番を土台と違う寸法で描いていて、そのままでは渡せなかった）。
- **書体が読めたことを確かめる。** 指定した書体が無いと、黙って別の書体で描かれることがある。使うフォントのファイルを描画に渡し、
  実際に読み込まれた書体を確かめる（下の「ブラウザ（WebGL）で描くとき」）。
- **本番の前に静止画で確かめる。** 時刻をいくつか選んで 1 枚に並べる。縮小した一覧だけでなく、**原寸の切り出し**も見る。

## ブラウザ（WebGL）で描くとき

three.js などをヘッドレスのブラウザで 1 コマずつ描くときの注意（2026-11-11 の制作で確かめた。条件は事例を参照）。

- **コマ番号を受ける関数を 1 つ公開し、時計に頼らない。** 壁時計や `requestAnimationFrame` の時刻で動くものを置かない。同じコマ番号なら同じ絵になる。
- **ヘッドレスは GPU を使わない（ソフトウェア描画）。** 1 コマが重く、測った速さは 4 コアで 3 プロセスを並べて合計で毎秒 0.6 コマほど（事例の速さの項）。
  本番の前に、数コマで 1 コマの時間を測る。
- **コマ番号の範囲ごとに別のプロセスで描き、できているコマは飛ばす。** 途中で止まっても続きから再開できる。直すときも、範囲だけを描き直す。
- **コマは画像で書き、書き出しは `write_video` に RGB の配列で渡す。** 画像の連番を自分の ffmpeg の引数で動画にしない（上の色の罠）。
- **書体は、読み込まれたものを確かめる。** コンテナに日本語のゴシック体が 1 つしか無く、Web フォントの取得も止められていたため、指定した書体がすべて黙ってゴシック体に
  落ちた。使えるライセンスのフォントのファイルをページへ自前で配り、`document.fonts` で読み込まれた書体を確かめて直した。

## 歌詞の連番を外部のツールで作るとき

歌詞の動きを外部のツール（ブラウザで動くもの）で作り、透過の連番として受けるときの観察（2026-11-11。ツールの一般的な性質の主張ではなく、そのときの見え方）。

- ツール自身のテンポの推定は、制作側が確かめたテンポの 2/3 だった。確かめた格子を、ツールへ渡して使った。
  拍の格子を `mv audio grid` で作るときの注意（探す範囲）は [audio](audio.md#実制作との比較)。
- 左右の余白（帯）の既定が、動きの多い 3D の絵には広すぎ、字が大きかった。帯を狭くした。
- 1 行を 1 つのカットで出すと、行全体が一度に出て約 5 秒止まっていた。2 列目を 1〜2 小節遅らせると、曲に付いて見えた。
- 1 行を 2 つのカットに分けると、一部の行で同じ語が両方の列に重なって出た。
- 語の時刻は、推定した行の時刻から小節の頭に置いたもの。**ボーカルとは照らしていない（実測ではない）。**

## 事例（2026-11-10）

初見のエージェントが、静止画 31 枚と 3 曲のつなぎから、73 秒・1080p の予告編を自前のスクリプトで描いた。合成素材ではない、実際の制作。

- 借りたもの: `mv fx guides`（4 枚で位置を読んだ）、`mv deliver join`（4 区間）、`mv sheet`（48 コマの確認）。
- 書き出しは自前の引数で行い、上の色の罠を踏んだ。`write_video` に替えて描き直した。差し替えは十数行だった。
- hooks の部品に気づかず、炎・刃の火・灯の点灯・稲光・雨を書き直した。README の入口の表に hooks の行を足したのは、このため。
- 半分の大きさの一覧では通った不具合（小さな灯が暗すぎる）が、原寸の切り出しで見つかり、本番の後に 1 区間を描き直した。
- 自前の描画の速さは 1 プロセスで毎秒 2〜3 コマ（2 コア）。fx のデモ（both 版・1080p）は同じ環境で毎秒 2.7 コマで、速さは自前で書く理由にならなかった。

## 事例（2026-11-11）

エージェントが、自前のレンダラで歌詞付きの MV の習作を作った。1 つの 3D 空間を three.js 0.170 で、ヘッドレスの Chromium（GPU なし）が 1 コマずつ描き、
カメラの構図を曲の小節で切り替える。最初は手本の動画の作りを写した 77 秒の習作で、そのあと絵・曲・モチーフを公開済みの作品のものに替えて、
92.3 秒（2,769 コマ・30 fps・絵は 1920×804 を 1920×1080 に黒帯でそろえた）にした。歌詞は外部のツールで作った透過の連番（2,109 コマ）を自前のスクリプトで重ねた。
作ったのは 2026-11-11、リポジトリの道具での測り直しは 2026-11-12。

- 借りなかったもの: クラウドのコンテナの uv が 0.11.32 で、必要な 0.13.5 に届かず `uv sync --locked` が止まった。「リポジトリの道具は動かない」と判断して、
  制作の最後まで使わなかった。`mv workflow plan` も作る前に実行しなかった。README のとおり uv を入れ直せばよく、このコンテナでは
  `pip install --user --break-system-packages "uv==0.13.5"` の 1 コマンドで入った（システムの Python は、ただの `pip install` を断る）。
- 作り直したもの: 歌詞の重ね（影・光彩・コマ番号のずらし。`mv overlay --layers` の `first_frame`・`missing: "transparent"`・`style.shadow`・`style.glow`・`style.tint`。
  [fx › overlay](fx.md#overlay透過レイヤーの重ね合わせfx-lyric-1) の例と同じ色の値まで書き直していた）、拍の格子（`mv audio grid`）、明滅を数えること（`mv gate flashes`）、コマを並べて見ること（`mv sheet`）、書き出し（`write_video`）。
- 色の罠: 2 回目。JPEG の連番を自前の ffmpeg に渡して踏んだ。測った値は上の「書き出しは `write_video` を使う」の 2026-11-12 の表。
- 速さ: 4 コアで 3 プロセスを並べ、2,769 コマが 1 プロセスあたり 4,381〜4,673 秒（約 73〜78 分）。合計で毎秒 0.6 コマほど（測定値）。ソフトウェア描画。
- コマ番号だけで決まる作りが効いた: あとで露出を直したときに描き直したのは 146 コマだけ。歌詞は別の透過の連番だったので、サビの歌詞の 6 案を、絵を描き直さずに見比べられた。
- 素材の差し替え: 骨組み（1 つの空間・カメラの構図の型・小節でのカット）は、絵・曲・モチーフ・拍の格子を替えるだけで別の曲に移せた。移らなかったのは、コマごとの明滅と、
  3D 空間の中に置いた歌詞（この作品では、明滅を外すように依頼があった）。
- 明滅を外したときの数字（明滅 = グリッチ（画面の乱れ）・音に合わせた点滅・稲光・文字の点滅・灯のまたたき・細かいカメラの揺れ・カットの閃光。外したあとの明るさは、ゆっくりした音量の包絡に従う）:
  - 自分で測った値（縮小したコマの差分）: キックの強いコマと弱いコマで、コマ間の変化の比が 1.75 → 0.99。平均の明るさ（sRGB の値 0〜1）が前後 5 コマの中央値から 0.01 を超えて外れるコマ
    （カットを除く）は 2,769 コマのうち 826 → 9。残った 9 は目で見て、リボンが横切る・速い寄り・歌詞の登場という動きで、点滅ではなかった。
  - `mv gate flashes` を既定（delta 0.10・1 秒に 3 回まで）で完成した 2 本に掛けると、前の版は変化 16（上がり 8・下がり 8）・明滅 1・組にならない 14・どの 1 秒でも最大 1・`pass`。外した版は変化 2（1・1）・明滅 0・最大 0・`pass`。
    見る人（依頼した人）が、この作品には明滅が多すぎると見た前の版も、既定では通った。既定は画面全体の大きな振れを数えるもので、好みは測らない（[gate](gate.md#完成動画の明滅を測るmv-gate-flashes)）。
  - `--delta 0.02` では、前の版は変化 360（180・180）・明滅 175・組にならない 10・最大 6・`fail`。外した版は変化 46（23・23）・明滅 14・組にならない 18・最大 2・`pass`。
  - 数は候補を挙げただけで、決めたのは目。
- `mv workflow plan --purpose lyric-mv` のあとに完成した制作へ `mv workflow check` を掛けると（2026-11-12、制作のあと）、全体は `incomplete`・終了コード 1、必要な 7 工程
  （`inputs`・`beats`・`lyrics`・`direction`・`assets`・`render`・`verification`）はすべて `pending`。検査はプロジェクトのフォルダの中だけを見るので、外で描いた動画・外で推定した歌詞の時刻・外の拍の格子を
  登録する口が無い。扱いは [workflow › 自前の描画で作った制作](workflow.md#自前の描画で作った制作は-lyric-mv-の工程に載らない)。
