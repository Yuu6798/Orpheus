# gate（書き出し前の検査と、歌詞の行・秒の確認表・実験的）

成熟度と実素材の確認範囲は操作ごとに記録する。[機能の成熟度](maturity.md) と `orpheus show ID` を参照。

書き出しの前に、機械で分かる問題だけを見つける道具。好みの判断はしない。

- **採点器ではない**: 字の時刻・UI 枠・重なり・拍・書き出しの揃い方だけを見る（明滅の回数は、頼んだときだけ測る。下記）。絵の良し悪しや作品としての採用は判定しない（採用は `accept` の人間の判定）。
- **決まりとの関係**: AGENTS.md の「生成物の開発中は測定器・検証器の機能を足さない」の例外として、2026-10-31 にユーザーが認めた。例外はこの `mv gate` の範囲だけ。
- **しきい値はどれも仮の値**: 最初の 1 作で確かめて直す。
- 動作確認は合成の timeline と `mv dance` のデモまで。行・秒の確認表だけ、第 1 作の分離ボーカルで試した（下記）。実作品の run ではまだ通していない。

## 1. 行・秒の確認表

```sh
uv run mv gate lines 歌詞.lrc 出力フォルダ --vocals vocals.flac
```

`--vocals` には `uv sync --locked --extra analysis` が要る。

- 入力は LRC か JSON（`[{"start": 秒, "line" か "text" か "display": 歌詞}, …]`）。`--vocals` にボーカルの Stem か分離音源を渡すと、推定の前後 `--window` 秒（既定 0.8）で歌い出しの立ち上がりを探す。
- 出力は `lines_table.csv`（試聴用。Excel で開ける UTF-8 BOM。確認の欄は空）と `lines_measured.json`（`mv gate check` に渡す）。
- `method`: `vocals_onset` = 実測 / `not_found` = 窓の中に候補が無く推定のまま / `estimate` = ボーカル無し。`mv gate check` は `not_found` と `estimate` の行を実測として照合しない（`method` が無い行は実測として扱う）。
- 行ごとの探索窓は、前後の行の推定時刻との中点で切る。前の行の結果より 0.08 秒以上後の候補だけを取る（短い行が続いても、同じ歌い出しを 2 行に当てない）。
- `ambiguous`: 2 番目の候補との上がり幅の差が 1.5 dB 未満で、どちらの立ち上がりか決め切れない行。確認表の `曖昧` の欄に `要確認` と出る。

**これは行頭の候補で、確定はユーザーの試聴。** 第 1 作の分離ボーカルで試した結果（2026-10-31）:

- 38 行のうち 31 行で実測でき、7 行は not_found。
- 人が詰めた行頭との差は中央値 0.07 秒、0.2 秒以内が 28 行、0.5 秒以内が 37 行。人の値の側がずれている行もある（1 行目は音量の形から見て実測の方が正しい）。
- 大きく外れた 1 行（0.74 秒）がある。語の途中の谷を拾うことがあるので、`上がり幅dB` が小さい行と not_found の行は特に聞いて確かめる。
- 実曲の行間は無音にならない（残響で -20dB 前後の谷）ので、無音からの立ち上がりではなく、谷から山への上がり幅で探す。

## 2. 検査

```sh
uv run mv gate check gate.json [--out DIR]
```

`gate.json` のパスは `gate.json` のあるフォルダ基準（絶対パスも可）で、`timeline` だけが必須。他は持っている分だけ書く。

```json
{
  "timeline": "dance_runs/<run_id>/timeline.json",
  "video": "dance_runs/<run_id>/dance.mp4",
  "master": "master.mp4",
  "expected_sha256": "…",
  "measured_lines": "lines_measured.json",
  "lyric_layers": ["band"],
  "confirmed": "confirmed.json",
  "confirmed_overrides_measured": true,
  "faces": "faces.json",
  "spec": "spec.json",
  "tracks": "tracks.json",
  "poses": "poses.json",
  "beats": "analysis.json",
  "flash": {"delta": 0.10, "max_per_s": 3},
  "thresholds": {"lead_max_s": 0.2, "overlap_mode": "time"}
}
```

| 検査 | 要るもの | 合格の条件（仮） |
|---|---|---|
| 歌詞の時刻 | `measured_lines`（`mv gate lines` の出力。層 `lyric_layer`（複数なら `lyric_layers`）の、`sung` が false でない行と順に照合） | 字が歌の 0〜0.2 秒前に出る。推定のままの行は見ず、一部なら要確認、全部なら未実施。`confirmed` に一致する行の外れは「要確認（試聴で確定済み）」で不合格にしない（`confirmed_overrides_measured`。既定 true） |
| 確認済みの時刻 | `confirmed`（`[{"text", "start"}]`） | 1 つも動いていない |
| 字と顔 | `faces`（`[{"start", "end", "box", "role"}]`。box は正規化座標）か `"faces": "auto"` と `"spec"` | 前の字が主役の顔に重ならない（出入りの間は可。z が behind の層は人物に隠れるので見ない）。顔の時刻はコマに丸める。推定の顔（`auto` の結果）との重なりは不合格にせず要確認にする |
| UI 枠 | timeline だけ | 0 コマ。箱に収まらない字（`overflow`）も不合格 |
| 揺れ | `tracks`（`{"名前": [[t, x, y], …]}`。画素） | 2 階差分の RMS 3 画素以下。3 点未満の要素は見ず、一部なら要確認、全部なら未実施 |
| つなぎ目 | `poses`（`[{"t", "points": [[x, y], …]}]`。正規化座標） | 切れ目の前後 2 コマ以内の骨格で姿勢の差 0.05 以下。超えたら要確認（切るコマの変更か `camera.seams` の提案）。時刻はコマに丸めてから前後を決める。1 コマ以内に `camera.seams` があれば、その設定を文言に添える。骨格が前後に無ければ要確認 |
| 字の重なり | timeline だけ | `exclusive` な層ごとに同時表示 0.1 秒以下（`exclusive` の無い 0.1 の timeline は back だけ）。見えている区間は、timeline の `lyric_fade` が `"after"`（無ければこれ。手書きの timeline）なら `[start, end + fade_out_s]`（フェードアウト込み）、`"inside"`（`mv dance` の出力。end の前でフェードアウトを終える）なら `[start, end]`。問題の行には 2 行の箱が交わるか（`box_intersects`）を添える。`thresholds.overlap_mode` が `"time_and_box"` なら箱が交わるときだけ数える（既定 `"time"`） |
| 拍 | `beats`（`downbeats`・`beats`・`beats_s`（`mv analyze` の出力）のどれかの配列）。無ければ timeline の `beats` | フラッシュと切れ目が**拍**（`beats` / `beats_s`。無ければ小節頭で代用）から 1 コマ以内。小節頭に合わせたいものは `flash_info` / `seam_info` の `align: "downbeat"`（dance の spec では `flashes[].align` / `clips[].align`。無ければ `"beat"`）で小節頭（無ければ拍で代用）と照合する。文面と集計は照合先ごと（「拍から」「小節頭から」、「N 件を拍と照合、M 件を小節頭と照合」）。`beat_exempt` の切れ目・フラッシュは「対象外（意図）」として数えるが、不合格にしない。blend の切れ目は blend の開始時刻を見る |
| 書き出し | `video`・`master`（任意で `expected_sha256`） | 全部のコマを復号できる、コマ数・尺が描いた区間（timeline の `interval`）と揃う、SHA-256 が控えと同じ、SSIM 0.98 以上 |
| 明滅（`flash` を書いたときだけ） | `flash`（`{"delta", "max_per_s"}`。既定値で測るなら `{}`）と、`master`（無ければ `video`） | どの 1 秒の窓でも、画面全体の明るさ（線形の相対輝度）の明滅が `max_per_s` 回以下（既定 3。変化は直前の山・谷から `delta` 以上、既定 0.10）。測り方と限界は下の「完成動画の明滅を測る」。**規格への適合を判定するものではない**。動画が無ければ未実施 |
| 顔の見切れ（`face_cut` を書いたときだけ） | `faces`（`mv gate faces` の `faces.json`。`visible` つき）と `face_cut`（`{"min_visible", "roles"}`） | `roles`（既定 main）の枠の `min_visible`（既定 1.0）以上が画面に入る。切れたコマは役と label ごとにまとめて**要確認**（不合格にしない）。`visible` の無い faces では未実施。下の「顔の見切れを数える」 |
| 重ねの字と顔（`overlay` を書いたときだけ） | `overlay`（`{"layers", "alpha", "roles"}`）と `faces` | `mv overlay` で重ねる透過の字（アルファ × 不透明度が `alpha` より大きい画素）が枠の中に無い。実測の主役の顔に重なれば**不合格**、推定の枠とほかの枠（手・扇など）は**要確認**。下の「重ねの字と顔」 |

`flash` を書かない gate.json では、明滅は測らず、検査は上の 9 つのまま（結果も合否も出力のファイルも、この検査を足す前と同じ）。

`"face_cut": {}` も同じく、書いたときだけ「顔の見切れ」の行を足す（下の「顔の見切れを数える」）。
`"overlay": {"layers": "layers.json"}` も、書いたときだけ「重ねの字と顔」の行を足す（下の「重ねの字と顔」）。

`"tail": {"max_tail_s": 1.0}` を書いたときだけ、`master`（無ければ `video`）の音の終わりと絵の終わりを測る「音の終わり」の行を足す（下の「完成動画の音の終わりと絵の終わり」）。音が切れてから絵が `max_tail_s`（仮の値。既定 1.0 秒）より長く続くときと、音が鳴っている所で終わるときは**要確認**（余韻の長さは好みなので、不合格にはしない）。音の無い動画・読めない動画は不合格、動画が無ければ未実施。測った報告は `tail_report.json`。

一部の区間だけ描いた run（`mv dance render --start/--duration`）は、timeline の `interval` の中に出るものだけを見る。確認済みの時刻だけは曲全体で見る。

`timeline` は `dance-timeline/0.1` と `0.2` の両方を読む（`src/mv_pipeline/dance/dance_timeline.schema.json` で検証し、知らない欄は無視する。形が違えばエラーで止まる）。独自のレンダラで仕上げた場合も、この形式で timeline を書けば検査できる。
`mv fx timeline render`（複数の fx ショットをつなぐ。docs/fx.md の timeline）の run の `timeline.json` もこの形。`0.1` に `beats`・`seam_info`（kind は `cut`・`xfade`・`black`・`flash`・`burn`）・`flash_info`（mode は `lerp_display`）を足したもので、字幕は無い。

**顔の推定（`"faces": "auto"`）** — `"spec"` に dance の spec のパスを書くと、dance の api から 2 コマごとに人物のアルファを取り、頭の帯から顔の箱を推定する。頭の帯は、fit の体の高さ（無ければその時刻のアルファの高さ）× 寄りの倍率の、上端から 12%。報告には「推定」と書く。

結果は 合格 / 不合格 / 要確認 / 未実施。**未実施は「材料が無くて見ていない」で、合格ではない。** 全体（`overall`）は、不合格が 1 つでもあれば `fail`（終了コード 1）、未実施があれば `pass_with_skips`、要確認があれば `pass_with_warnings`、なければ `pass`。

出力先は既定で `gate.json` の隣の `gate_report/`: `gate_report.md`・`gate_report.json`・問題のコマの静止画（検査ごとに最大 12 枚）。stdout は短い JSON。`flash` を書いて動画を測ったときは、測定の詳細 `flash_report.json` も同じフォルダに書く。

## 3. 正解の分かっている試験素材（`mv gate demo`）

```sh
uv run mv gate demo projects/gatedemo                 # 既定: 4 行（2 行目は 0.333 秒早く、4 行目は正解の 0.05 秒後）、拍に置いたフラッシュ 5 件
uv run mv gate lines projects/gatedemo/lyrics.lrc projects/gatedemo/lines --vocals projects/gatedemo/vocals.wav
uv run mv gate check projects/gatedemo/gate.json      # expected.json の checks と比べる。既定では歌詞の時刻が fail（終了コード 1）、拍が pass
```

書くもの: `vocals.wav`（声の代役。行ごとに正解の歌い出しから持続する倍音の音。立ち上がり `--attack-ms`、背景の雑音 `--floor-db`）、`lyrics.lrc`（宣言した行の時刻 = 正解の 0.1 秒前 + `--shifts`）、`timeline.json`（手書きの dance-timeline/0.1。層 band の行・フラッシュ・拍の格子）、`beats.json`（`--bpm`・`--beats-per-bar`。`--no-downbeats` で小節頭を省く）、`gate.json`、`expected.json`（行ごとの正解の歌い出し・宣言・期待する lead と合否、フラッシュごとの照合先からのずれと合否、検査ごとの期待する結果）。`--flashes` と `--flash-align beat|downbeat` でフラッシュの位置と照合先を変えられる。

正解はすべて素材の設計値で、推定ではない。音は倍音だけで子音も残響も無いので、実曲の歌い出しの推定精度の確かめにはならない（工程の接続と検査の論理を確かめる素材）。CI はこの素材で demo → lines → check → expected の照合を回す。`--vocals` の WAV は soundfile が無くても読める（他の形式は analysis extra）。

## 既定の合否が変わった変更

- 2026-11-08（字の重なり）: `lyric_fade` の無い timeline（手書き）は、見えている区間をフェードアウト込み `[start, end + fade_out_s]` で数える。前の行が `end` で消えたことにして「超過 0」だった、フェードアウト中に次の行が出る timeline は、重なりが 0.1 秒を超えれば不合格になる（例: `end=3.0`・`fade_out_s=0.3` の次に `start=3.0` の行 → 0.300 秒）。`mv dance` は行を `end` の前でフェードアウトし終えるので、この変更から timeline に `lyric_fade: "inside"` を書き、重なりは `[start, end]` で数える（**この変更より前に描いた dance の run は `lyric_fade` が無く after として読むので、フェードの分だけ重なりが増えて不合格になりうる。描き直すか timeline に `"lyric_fade": "inside"` を足す**）。別の列に置いた 2 行を重なりと数えたくないときは `thresholds.overlap_mode: "time_and_box"`。Remotion で描いたテロップのデモで見つかった。
- 2026-11-08（GATE-3）: 拍の検査の照合先を「小節頭があれば小節頭」から「既定は拍（`align: "downbeat"` のものだけ小節頭）」に変えた。小節頭の配列を持つ timeline で、拍に置いたフラッシュ・切れ目が不合格だったものは合格になる。小節頭に合わせたい出来事は `align: "downbeat"` を書く（書かないと拍と照合するので、小節頭からのずれは見つからない）。Remotion で描いたテロップのデモを `mv gate check` に掛けたとき、拍のフラッシュ 5 件が「小節頭と照合、ずれ 4」で止まったことから。

## 連番から timeline を起こす（`mv gate timeline`）

Remotion などで描いた透過の連番（PNG。straight α）から、字が**実際に見えているコマと範囲**を α で実測し、`mv gate check` が読む dance-timeline/0.1 を書く。宣言（props の時刻）と実測の差を行ごとに出す。

```sh
uv run mv export remotion-props projects/song-a --out props.json --beats-per-bar 4
uv run mv gate timeline --frames out/line1:lyric-001 --frames out/line2:lyric-002 --lyrics props.json --layer band --out timeline.json
uv run mv gate timeline --frames out/all --hints hints.json --lyrics props.json --layer band --out timeline.json   # 1 つの連番に全行
uv run mv gate check gate.json      # {"timeline": "timeline.json", "beats": …} 
```

- 行の切り分けは、行ごとに別の連番（`--frames DIR:行の id`）か、1 つの連番と行ごとの領域の手がかり（`--hints` = `{行の id: 正規化した箱}`。箱の中の不透明な画素をその行と見なす）。props の行が 1 つだけなら手がかりは要らない（あればその箱の中だけを見る）。
- 「見えている」は α > `--alpha-threshold`（既定 64）の画素があること。行の最初と最後に見えるコマ（end は最後のコマ + 1）と、見えている全コマの不透明な画素を覆う箱（正規化）を測る。
- 宣言と実測の差（例「開始が 1 コマ遅い」「途中で見えないコマ 2」）は `<out の stem>_measured.json` と stdout の要約に出す。どちらが正しいかは決めない。見えているコマが無い行は、timeline に宣言の時刻のまま残し（`measured: false`。行数を props と揃え、`mv gate check` の行の対応を崩さない）、要約の `unseen_lines` に出す。`mv gate check` はこの行を実測として扱わない（歌詞の時刻では「実測できず見ていない行」として要確認、字と顔・UI 枠・字の重なりには出さない）。
- 連番のコマ数は props の `duration_frames` と同じでなければならない（途中だけ描いた連番は測れない）。アルファの無い連番はエラー。並びは数字の大小（`frame2` < `frame10`）。
- 拍・小節頭は props からそのまま秒に直して写し（丸めない）、フラッシュは props に無いので `--flashes 5.5,6.0`（秒）で与える。書く timeline は実測なので `fade_in_s` / `fade_out_s` は 0、`lyric_fade` は inside、`exclusive` は true。連番の各コマ（読んだバイト列から 1 回で計算）と props・使った hints の sha256 は timeline の `measured.sources` に残る。
- 確かめたのは合成の連番（numpy で描いた箱）だけ。実際の Remotion の連番では未確認。

## 完成動画の明滅を測る（`mv gate flashes`）

hooks で足した光（拍に合わせた閃光など）は timeline に載らないので、描き終えた動画そのものから、画面全体の明るさの明滅を数える。timeline は要らず、完成した動画 1 本だけに掛けられる。

```sh
uv run mv gate flashes final.mp4 [--out DIR] [--delta 0.10] [--max-per-s 3]
```

- **機械で測った回数の報告で、規格への適合を判定するものではない。** 既定値は、広く使われている目安（1 秒間に 3 回を超える明滅を避ける。変化の大きさは最大の明るさの 10%）に合わせた仮の値。`pass` は「この測り方で上限を超えなかった」だけを意味し、放送・配信の基準への適合や、見る人への安全を示さない。光の強さや速さの好みも判定しない。
- 測り方:
  1. **明るさ = 線形の相対輝度**: コマを小さく読み（幅 320 画素までの面積平均。色の行列はタグによらず BT.709 として読む）、表示の値を sRGB の伝達特性で画素ごとに線形へ戻し（fx・dance の合成と同じ式）、`0.2126 R + 0.7152 G + 0.0722 B` を画面全体で平均する（0〜1）。`--delta` はこの値に対するしきい値で、ガンマのかかった表示の値の差ではない（灰色 128 は 0.216、188 が 0.503）。コマの間隔が一定でない動画（可変フレームレート。ffmpeg の情報の平均 `fps` と基準 `tbr` が違うもの）は、ffmpeg の `fps` フィルタで基準のフレームレートに揃えた一定の間隔のコマにしてから測る（1 秒の窓がコマ数と合うように。コマ番号と秒は揃えた後のもの）。平均のフレームレートに揃えると、コマの詰まった区間の光が落ちて数えられないので、基準に揃える。基準が 240 fps を超えるときは、測らずにエラーで止まる（`mv gate check` では「明滅」の行だけ不合格）。コマの間隔が一定の動画（平均と基準が同じ）は、揃えずにそのまま測る。
  2. **変化**: 明るさが、直前の極値（山か谷）から `--delta` 以上離れること（しきい値つきのジグザグ）。離れたコマで 1 つの変化とし、向きを反転して次の極値を追う。変化の時刻は、しきい値を越えたコマ。上がりと下がりは必ず交互になる。数コマかけた上がりも、ゆっくり消える光の戻りも、山・谷からの差が合計で `--delta` に達したコマで 1 つの変化になる。`--delta` 未満の揺れは変化にしない。最初の変化までは、それまでの最小と最大の両方を極値として見る。
  3. **明滅**: 隣り合う 2 つの変化（暗 → 明 → 暗、または明 → 暗 → 明）で、コマの差が 1 秒未満の組を 1 回と数える。前から順に、重ならないように組にする。片方向だけの変化（場面の切り替え・単調なフェード）と、1 秒以上離れた 2 つの変化は明滅にしない。
  4. **1 秒の窓の回数**: その 1 秒（あるコマへの変わり目から、fps コマ未満の変わり目まで）の明るさだけに 2 を掛け直し、隣り合う 2 つの変化を前から組にした数。窓の前の明るさは使わない。動画全体で取った変化から数えると、窓の前の変化が回数を減らすことがあるため（明るい場面への切り替えの後の最初の光は、上がりが切り替えの上がりに吸収される。暗くなる切り替えは、組を 1 つずつずらす。どちらも、1 秒に 4 回の光が 3 回と数えられる）。そのため、`changes`・`flashes`（動画全体）と、窓の回数・組が違うことがある。窓は 1 コマずつずらして全部見る。どの窓でも最大の回数（`max_per_window`）が `--max-per-s` を超えたら `status` は `fail` で、終了コード 1（gate のほかの検査の不合格と同じ扱い）。
- 出力は既定で動画の隣の `<動画の名前>_flash_report/flash_report.json`（`--out` でフォルダを変える）。stdout は短い JSON。
  - `video`（名前・sha256・平均のフレームレート `fps`・基準のフレームレート `base_fps`・測ったコマ数 `frames`・寸法・色の行列のタグ）、`thresholds`（`delta`・`max_per_s`・`window_s`）。
  - `read`: 測り方。読んだ大きさ `size`、測ったコマのフレームレート `fps`、一定の間隔のコマに揃えたか `resampled`（true なら `video.frames`・コマ番号・秒は揃えた後のもの）、色の行列 `matrix`（`bt709`）、線形に戻す式 `transfer`（`srgb`）、係数 `weights`、`brightness`（`relative_luminance` = 線形の相対輝度）、`change`（`delta_from_last_extremum` = 直前の極値から `delta` 以上）、`window`（`recounted_from_its_own_frames` = 窓の回数は、その窓の明るさだけで数え直す）。
  - `changes`: 変化の一覧（動画全体に 2 を掛けたもの）。`frame`（しきい値を越えたコマ）・`t`（秒 = コマ / fps）・`direction`（`up` / `down`）・`amount`（大きさ = 山から谷までの差）・`from` / `from_frame`（離れる前の極値とそのコマ）・`to` / `to_frame`（変化の後に着いた極値とそのコマ。最後の変化は動画の終わりまでの極値）。
  - `flashes`: 明滅の一覧（`changes` を 3 で組にしたもの）。`frame` / `t`（1 つ目の変化）・`return_frame` / `return_t`（2 つ目の変化）・`order`（`up_down` = 暗 → 明 → 暗、`down_up` = 明 → 暗 → 明）・`amount`（2 つの変化の小さい方）。
  - `counts`（動画全体の変化・上がり・下がり・明滅・組にならなかった変化の数）、`max_per_window`（どの 1 秒の窓でも最大何回か）、`busiest_window`（最も多い窓。始まりのコマと秒・その窓で数え直した変化の数と組のコマ。同じ回数なら早い窓で、始まりは最初の変化に寄せる。明滅が無ければ null）、`status`。
  - 同じ動画と同じしきい値なら同じ報告になる（時刻や絶対パスは書かない）。
- `mv gate check` は、gate.json に `"flash": {"delta": 0.10, "max_per_s": 3}` を書いたときだけ、`master`（無ければ `video`）に同じ測定を掛けて「明滅」の行を足す。行の文には、動画全体の変化・明滅の数と、1 秒の窓ごとに数え直した最大の回数を書く（合否は後者で決まる）。超えたら不合格で、問題の一覧に最も多い窓を出す（時刻はほかの検査と同じショットの時刻で、一部の区間だけ描いた run では `interval` の開始を足す。ミリ秒に切り捨てるので、静止画は窓の最初の変化のコマになる）。「明滅」の静止画は測った動画（`master` があれば `master`）から取り、ほかの検査の静止画は今までどおり `video` から取る。`master` も `video` も無ければ未実施、動画を読めなければ不合格（ほかの検査の結果は残る）。`flash` の知らない欄や範囲の外の値は、検査を始める前にエラーで止まる。
- 確かめたのは合成の動画（1 色で塗ったコマに、白い閃光・ゆっくり消える光・緩い明暗を置いたもの。コマの間隔が一定でない動画は、最初の 1 秒に 4 回の閃光を置いて残りのコマを 0.5 秒ずつにしたもので、平均 4.11 fps・基準 30 fps。揃えずに数えると 1 回、平均に揃えると 0 回、基準に揃えると 4 回）と、デモの描画 2 本（どちらも合成素材。2026-11-11、24 fps、既定のしきい値）:

## 完成動画の音の終わりと絵の終わり（`mv gate tail`）

完成した動画 1 本の、音が切れる時刻と、そこから絵が続く長さを出す（timeline は要らない）。リポジトリ外の 2 作目の VRM のダンスの演出版で、
曲の音が切れてから絵が 2.1 秒続いて「余韻がちょっと長い」と言われ、0.5 秒に直した。書き出しの前にその数を見るための道具（2026-11-16 に
ユウが足してよいと決めた新しい検査）。**数を出すだけで、余韻の良し悪しは判定しない。**

```sh
uv run mv gate tail final.mp4 [--out DIR] [--max-tail-s 1.0] [--window 0.1] [--floor-db -60]
```

- 音が切れる時刻（`audio_end_s`）は `mv audio end` と同じ測り方（[audio](audio.md#音の終わりmv-audio-end)）で、映像の最初のコマから数える（音の流れが映像より遅れて始まる動画は、その差 `audio_start_s` を足す。報告の窓の時刻も同じ）。絵が続く長さ（`picture_after_s`）は、映像の長さ（コマの数 ÷ fps）− 音が切れる時刻。
- `status`: 絵が `--max-tail-s`（仮の値。既定 1.0 秒）より長く続くか、最後の窓まで音が鳴っていれば `warn`（理由を `reasons` に書く）。ほかは `pass`。音の無い動画は測らずに止める。終了コードはどちらも 0。
- 出力は既定で動画の隣の `<動画の名前>_tail_report/tail_report.json`（`gate-tail-report/0.1`）: 動画の名前と sha256・fps・コマの数・長さ、測り方、しきい値、測った数、終わりの 5 秒の窓ごとの dBFS、`status` と `reasons`。同じ動画・しきい値・復号環境なら同じ報告。
- AAC の末端を使う `cut_while_sounding` と警告は、FFmpeg の復号差を受ける。2026-11-20 の合成テストでは、今回使った 7.1.5 で期待する `warn` が `pass` になり、imageio-ffmpeg 同梱 9.0.2 では期待どおりだった（[音の終わりの環境差](audio.md#音の終わりmv-audio-end)）。以下の実素材照合から、FFmpeg の版をまたいだ判定の一致までは保証しない。

## 3D で描いた動画の書き出しの表（`mv gate final`）

model3d で描いて書き出した動画の検査を、1 枚の表にする。リポジトリ外の 4 作目の 3D のダンスで、本番の書き出しのたびに、動画の構造・取り出したコマの照らし合わせ・最後のコマ・影の領域のあふれ・描画の秒を、使い捨ての台本で表にした（動画の構造は `ffmpeg -i` の表示を自分で読んでいた）。それを、今ある部品を呼ぶ形にした（2026-11-23。4 作目の持ち帰りの決めごと）。**数と合否の行を並べるだけで、絵の良し悪しは判定しない。**

```sh
uv run mv gate final final.mp4 --video-frames video_frames.json --show show.json [--show show2.json …] [--frames 918] [--out DIR]
```

| 行 | 何を | 不合格 |
|---|---|---|
| `structure` | 動画の構造（fx の `probe.check_video`。復号・大きさ・fps・コマの数・音・BT.709 の印）。期待の大きさ・fps・コマの数は、省くと `--show` の報告から埋める（大きさと fps はどの報告も同じとき、幅と高さは別々に。コマの数は描いた T を合わせた数が 1 ずつ続くとき）。コマの数と fps が分かれば、音の長さ（コマの数 ÷ fps）も比べる。分からないまま見なかった期待があれば `partial`（`unchecked` に並べる。全体は `incomplete`） | 構造の失敗（`technical_pass` が偽）。音の無い動画（`--no-audio` なら音が無いこと）・色の印の無い動画も |
| `video_frames` | model3d の `check.video_frames` の報告（動画から取り出したコマが、仕上げたコマの同じ T に合うか）。報告の `video_sha256`（比べた動画の sha256）が、検査する動画の sha256 と同じかも確かめる。`video_sha256` の無い報告は、どの動画と比べたか分からないので `not_recorded` | 合わないコマがある。報告の動画の sha256 が違う（同じ名前に書き出し直した動画の、古い報告も） |
| `last_frame` | 最後のコマの明るさ（R・G・B の平均。0〜1。BT.709 の印の動画は BT.709 の式で読む） | `--min-last-mean`（既定 0.02。黒に近い）より暗い。暗転で終わる動画は `--min-last-mean 0` |
| `shadow_overflow` | model3d の `render.show` の報告（区切って描いたなら全部）の、影の領域のあふれの行数（`shadow_overflow.lines`）の和と、必要がいちばん大きい行の「必要 / 上限」 | 1 行でもある |
| `render_seconds` | 同じ報告の、描いたコマの数と秒（数だけ。合否は無い） | — |

- **全体の `status`**: どれかの行が不合格なら `fail`（終了コード 1）。不合格が無く、渡していない行（`not_run`）か、記録の無い行（あふれを数える前の `render.show` の報告・`video_sha256` の無い `check.video_frames` の報告。`not_recorded`）か、見ていない期待のある構造の行（`partial`）があれば `incomplete`（終了コード 0。合格扱いにしない）。全部の行が合格なら `pass`。報告が JSON の辞書でなければ止める。
- mv_pipeline は model3d を import しない（逆も同じ。つなぎはファイルだけ）。3D の側の行は、model3d の工程が書いた報告のファイルを読む。`check.video_frames` は先に model3d のレシピで回しておく。
- 出力（既定は動画の隣の `<動画の名前>_final_report/`）は final_report.json（`gate-final-report/0.1`）: 動画の名前と sha256・大きさ・fps・コマの数・音の有無、行ごとの数と `status`・`summary`、`render.show` の報告ごとの数。
- **確かめたこと**: CI では、合成の小さな動画（BT.709 の印と無音の音つき・音なし・色の印なし・最後のコマが黒）と、手で書いた `render.show`・`check.video_frames` の報告で、合格の表、音の無い動画・色の印の無い動画・暗転した最後のコマの不合格、報告が無いときの `incomplete` と構造の `partial`、あふれの行の不合格と、あふれを数える前の報告の `not_recorded`、別の動画の報告と、同じ名前に書き出し直した動画の古い報告の不合格（同じ中身の写しは合格）、`video_sha256` の無い報告の `not_recorded`、大きさとコマの数の違い（`--show` から埋めた期待・幅だけ渡したときの高さも）、辞書でない JSON と悪い入力、コマンドの終了コードを確かめた。
- 2026-11-23 に、リポジトリ外の 4 作目の 3D のダンスの完成した動画（1080×1920・918 コマ・30 fps。読むだけ）に掛けた（実測）。
  - `structure` 合格（918 コマ・BT.709・音 30.6 秒）、`last_frame` 合格（明るさの平均 0.538。使い捨ての台本は 0.534。台本は ffmpeg の既定の変換で PNG にしてから測ったので、色の式の分だけ違うと見ている）。

  - `render.show` の報告は、描き直した 61 コマのもの（あふれを数える前の版）だけで、`shadow_overflow` は `not_recorded`、`render_seconds` は 61 コマ 373.4 秒。表の全体は `incomplete`（本番の描画の報告が無いため。合格扱いにしない）。

## 顔の見切れを数える（`mv gate faces` と検査の `face_cut`）

縦の画面に横の絵を写すと、寄りで顔が窓の端に掛かりやすい。2026-11 に完成した MV の縦の Shorts では、ユーザーがスマホで 3 カットの顔の見切れを
見つけ、カメラを動かして直した。その確かめを、描かずに全部のコマで数える道具（2026-11-21 にユウが足してよいと決めた新しい検査）。
**切れたコマを数えるだけで、良し悪しは判定しない**（寄りで額や顎を切るのは演出のこともある）。

```sh
uv run mv gate faces timeline.json --out faces_out [--start S] [--duration D] [--extra boxes.json] [--min-visible 1.0]
```

- 入力は fx の timeline（`fx-timeline/0.2`）。枠は spec のショットは spec の `faces`、動画のショットは timeline のショットの `faces`
  （元画像・動画の正規化座標。[カメラの視野と顔の枠](fx.md#カメラの視野と顔の枠fx-shot03)）。
- `--extra`（`gate-boxes/0.1`）で、spec を変えずにショットごとに枠を足せる（手・扇など、字を重ねたくない物にも使える）:

  ```json
  {"schema_version": "gate-boxes/0.1",
   "boxes": [{"shot": "shots/a.json", "box": [0.40, 0.70, 0.46, 0.82], "role": "other", "label": "手", "estimated": true}]}
  ```

  `shot` は timeline のショットの `spec`（動画のショットは `video.path`）と同じ文字列か、ショットの番号（0 から）。同じ spec のショットが
  いくつもあれば、どれにも足す。`role` は `main` / `other`（既定 `other`）、`estimated` は既定 `true`。知らない鍵は止まる（`x_` で始まる鍵は書ける）。
- 写し方は `mv fx timeline render` が書く `faces.json` と同じ（コマの時刻 start + i/fps のショット。xfade・burn の間は入ってくるショット。
  camera の層で写し、深度視差は入れない。拍の脈は入れる）。描画はしないが、ショットの素材は読む（fx extra が要る）。
- 出力:
  - `faces.json`: `[{"start", "end", "box", "role", "estimated", "visible"[, "label"]}]`。`box` は画面の外を切った箱（画面の正規化座標）で、
    `mv gate check` の `faces` にそのまま渡せる。`visible` は、写した枠の面積のうち画面に入っている割合（0〜1）。
    画面から全部出た枠も、面積 0 の箱と `visible` 0 で残す（面積 0 の箱はどの字とも交わらないので、「字と顔」の結果は変わらない）。
  - `faces_report.json`（`gate-faces-report/0.1`）: ショットごとの、主役の枠の `visible` が `--min-visible`（既定 1.0。少しでも切れたら数える）
    より小さいコマの数、最小の `visible`、切れた辺（left・top・right・bottom）、最初と最後のコマの時刻。stdout には、切れたショットだけを出す。
- `mv gate check` の設定に `"face_cut": {"min_visible": 1.0, "roles": ["main"]}` を書くと、「顔の見切れ」の行を足す
  （書かなければ、検査も報告も今までどおり）。`faces` の `visible` が `min_visible` より小さいコマを、役と label ごとに続いたコマへまとめて
  問題にする。描いた区間（timeline の `interval`）の外の枠は見ない。切れていても**要確認**で、不合格にはしない。`visible` の無い `faces`
  （手で書いた枠や `mv fx timeline render` の `faces.json`）では未実施。
- **確かめたこと**:
  - CI では、合成の横長の絵の上で縦の窓を横へ動かし、枠が右の辺から出ていくコマ数・`visible` の値（窓の幅から計算した値と 0.005 以内）・
    全部外の枠・`--extra`・`--min-visible`・`mv gate check` の行と静止画・コマンドを確かめた。画面に入っている枠は `mv fx timeline render` の
    `faces.json` と同じ記録になることも確かめた。
  - 実素材（2026-11-21）: 2026-11 に完成した MV の縦の Shorts 2 本の timeline に、制作の検査の台本と同じ顔の全体の枠（目測の推定。
    8 カット）を `faces` として書いて通した。採用版（r2）はどちらも切れたコマ 0（807 コマ・838 コマ）で、制作の検査と同じだった。
    指摘を受ける前の版（r1）では、1 本目で 97 コマ（2 カット。最小 0.808・0.937）、2 本目で 74 コマ（1 カット。最小 0.832）が切れていて、
    ユーザーがスマホで指摘した 3 カットと同じだった。制作の検査の台本（コマの画素の中心で角を写す）を同じ r1 に掛けた値とは、
    コマごとの `visible` の差が最大 0.0009（507 コマ）で、切れたコマの数は同じだった。

## 重ねの字と顔（検査の `overlay`）

`mv overlay` で重ねる透過の字（外で書き出した歌詞の連番や、題字のカード）は timeline の字の箱に無いので、「字と顔」では見ない。
2026-11 に完成した MV の本番では、確認版（960×540）の目視で見落とした字と手の重なり（1 行・38 コマ）を、本番の大きさの全部のコマを
数える自前の台本で見つけて直した。その数え方を gate の行にしたもの（2026-11-21 にユウが足してよいと決めた新しい検査）。
**重なった画素を数えるだけで、字の読みやすさや置き場の好みは判定しない。**

```json
{"timeline": "fx_runs/…/timeline.json", "faces": "faces_out/faces.json", "video": "overlay.mp4",
 "overlay": {"layers": "layers.json", "alpha": 26, "roles": ["main", "other"]}}
```

- `layers`: `mv overlay --layers` に渡す設定（fx-overlay-layers/0.1。gate.json のあるフォルダ基準）。連番の `first_frame`・`missing`・`resize`・
  `opacity` と、時刻つきの 1 枚の画像（`start_s`〜`end_s` と出入り）は `mv overlay` と同じに読む。出力の 0 コマ目は、描いた区間（timeline の `interval`）の頭のコマ。
- 字: どれかの層の アルファ（0..255）× 不透明度 が `alpha`（0〜254 の整数。既定 26。約 0.1）より大きい画素。仕上げ（`style` の影・光彩・後光）で広がる分は数えない。
- 枠: `faces` のうち `roles`（既定は main と other）の枠。`mv gate faces` の `faces.json`（コマごと）を渡すのがよい。
  手・扇など、顔のほかに字を重ねたくない物は `mv gate faces --extra` で `label` を付けて足す。手で書いた区間の枠でもよい（コマの時刻 t が start ≤ t < end の枠を当てる）。
- 数え方: コマ・枠ごとに、箱が掛かる画素（左上は切り捨て、右下は切り上げ）の中の字の画素を数え、役・label・推定かどうかごとに、続いたコマの重なりへまとめる。
- 結果: 実測の主役の顔（role main・estimated false）に重なれば**不合格**。推定の主役の顔と、ほかの枠は**要確認**。問題の時刻は、その重なりで画素がいちばん多いコマ
  （静止画も `video` のそのコマ）。`overlay_report.json`（`gate-overlay-report/0.1`）に、照合したコマと枠の数、重なりごとの役・label・最初と最後のコマの時刻・コマ数・
  最大の画素数とそのコマの画素の範囲を書く。
- `resize` の層の大きさが出力と違うときは、縮めるのに cv2 を使う（fx extra）。
- **確かめたこと**:
  - CI では、合成の連番（横に動く字の四角）と手で書いた枠で、重なりの画素数とコマ数（計算した値と同じ）、端の画素、しきい値と不透明度、無いコマ、
    時刻つきのカード、描いた区間の外の枠、コマ数の食い違い、`mv gate check` の結果と出力を確かめた。
  - 実素材（2026-11-21）: 2026-11 に完成した MV の本編（1920×1080・5,544 コマ）に、制作の検査の台本と同じ枠（主役の顔・仮面・ほかの人の顔・手・扇。目測の推定 76 個）を
    `mv gate faces --extra` で足し、歌詞の連番（3,620 コマ）で通した。
    - 採用した版は重なり 0（照合した 2,729 コマ・4,684 枠）で、制作の検査と同じ。題字のカードも入れた制作の重ねの設定そのままでも 0。
    - 直す前の版（問題の 1 行を直す前の連番）は、手の枠の重なり 1 件（最大 1,003 画素の 117.5 秒のコマと、その画素の範囲が制作の検査と同じ）。
      重なったコマは 37 で、制作の 38 より 1 少ない。違う 1 コマは、制作の台本がショットの始まりの時刻を四捨五入したコマに割り当てていたもの
      （そのコマの時刻では、まだ前のショットが写っている。gate は描いたときと同じく、コマの時刻のショットで写す）。
    - 全部のコマ・枠で比べると、両方が同じショットを見ているコマ・枠の組 3,967 で、字の画素の数がすべて同じだった。
    - 採用版の縦の Shorts 2 本を、見切れの検査と同じ顔の全体の枠（髪まで含む大きめの推定の枠）で通すと、3 か所（75・65・126 コマ）が要確認になった。
      どれも縦組みの字の列が枠の左側に掛かる所で、その版はユーザーが見て採用している（要確認は不合格ではない。枠を大きく取るほど要確認は増える）。

## 分離ボーカルの数字（`mv gate voice`・`notes`・`repeat`）

分離ボーカル（Stem か分離音源）から、歌詞の行の頭・終わり・息継ぎや、同じ旋律の繰り返しを探すための数字を出す。手順は実制作の
歌詞の時刻の台本と同じ。**数字を出すだけで、合否も良し悪しも出さない。行の時刻の確定はユーザーの試聴**（`mv gate lines` の
確認表と同じ）。librosa が要る（`uv sync --locked --extra analysis`）。

```sh
uv run mv gate voice vocals.flac [--from 0 --to 60] [--threshold-db -32] [--gap-s 0.14] [--min-s 0.08]
uv run mv gate notes vocals.flac --from 21.0 --to 26.5
uv run mv gate repeat vocals.flac --ref 66.0 72.0 --search 125 140 [--top 3] [--include-end]
```

- 結果は stdout の JSON（記録の全部）。`--out` を付けたときだけファイルにも書く（ボーカルと同じファイルには書かない。中身の違う
  ファイルは `--force` が要る）。
- **voice**（`gate-voice/0.1`）: 声の出ている区間。行の頭・終わり・息継ぎの候補を探す。
  - 元のサンプリング周波数のまま読み、左右を平均したモノの `[--from, --to)` を、librosa の `rms`（窓 30 ms・hop 10 ms。窓の中央が
    そのコマの時刻）で dB にし、95 パーセンタイルを 0 dB とする。`--threshold-db`（既定 −32）を超えるコマの続きを区間にし、
    前の区間との間が `--gap-s` 未満ならつなぎ、`--min-s` 未満の区間は捨てる。
  - `segments`: `start`・`end`・`length_s`・`gap_before_s`（前の区間との間。長いほど行や句の切れ目の候補）。
  - 基準は 95 パーセンタイルなので、声が範囲の 5% より短いと雑音の床が基準になり、雑音まで声と数える。歌っている所を含む範囲で使う。
  - コマの時刻は「範囲の頭 + コマ × hop の標本数 ÷ 周波数」。実制作の台本は「コマ × 0.01 秒」と数えるので、0.01 秒がちょうどの
    標本数にならない周波数（22050 Hz など）では後ろほど遅れる（22050 Hz の 31 秒で 70 ms）。44100・48000 Hz では同じ値。
- **notes**（`gate-notes/0.1`）: 範囲の中の音符。行の頭を音符の数（拍・モーラの数）で数えるのに使う。
  - `[--from, --to)` を 16000 Hz に変換し、pYIN（150〜1000 Hz、窓 1024・hop 160 = 10 ms）の音程を半音に丸め、同じ半音が 7 コマ
    （70 ms）以上続く所を 1 音とする（`notes`: `start`・`end`・`midi`・`name`）。同じ高さの音が続くと 1 音にまとまるので、数は
    ±1〜2 ずれることがある（実制作の目安）。
  - `onsets_s`: 立ち上がり（`onset_detect`、delta 0.12・間隔 6 コマ）。`dips`: 音量（`rms` 窓 640・hop 160）が 95 パーセンタイル
    から −14 dB 未満のまま 6 コマ（60 ms）以上続く谷（息継ぎや行の切れ目の候補）。
  - pYIN は重いので、範囲を短く切って使う（数秒の範囲で 1〜2 秒）。
- **repeat**（`gate-repeat/0.1`）: 同じ旋律の繰り返し（2 番のサビなど）の時刻を、1 番の時刻 + ずれで求める。
  - `--ref` の範囲の音程の並びを、`--search` の範囲の中で 10 ms ずつずらして比べる。両方に音程があるコマが基準の 30% 以上ある
    ずらし方だけを数え、半音の差（12 半音の差は折り返す）が 1 未満のコマの割合を一致率（小数 3 桁）とする。
    ずれ = 探す範囲の頭 + ずらした量 − 基準の範囲の頭（秒、2 桁）。
  - `matches`: 一致率の高い順に `--top` 件（同じ一致率なら、ずれの大きい順）。実制作の目安では、一致率 0.9 前後なら確度が高く、
    0.6 前後は補助。
  - 既定では、実制作の台本と同じく、探す範囲の終わりにぴったり合うずらし方（最後の 1 つ）は比べない。
    - 繰り返しが探す範囲の終わりにぴったり来ると、正解より 10 ms 前が 1 位になる。合成の旋律では、正解の 5.37 秒（一致率 1.0）の
      代わりに 5.36 秒（0.987）が出た。
    - 探す範囲が基準より 10 ms 足らず長いだけだと、比べるずらし方が 1 つも無い（`shifts_compared` が 0 で、`matches` が空）。
    - `--include-end` を付けると、最後の 1 つも比べる。付けないときは、探す範囲を繰り返しの前後に余裕を持たせて取る。
- **合成の声で確かめたこと**（2026-11-11）:
  - 実制作の台本をそのまま写した関数と、44100 Hz・48000 Hz の合成の旋律（倍音のある音で G4・A4・B4・C5・B4・A4 を 0.25 秒ずつ、
    2 回）で、区間・音符・立ち上がり・谷・繰り返しのずれと一致率が値まで同じ。
  - 合成の旋律では、音程はすべて正しく、音の頭は 25 ms 以内、繰り返しのずれは正解の 5.37 秒（一致率 1.0）。
  - `mv gate demo` の声の代役（立ち上がり 30 ms）では、`voice` の区間の頭は正解の 10 ms 前、終わりは 10〜20 ms 後（窓の中央の
    時刻で数えるため）。`gate lines` の歌い出しの偏り（約 20 ms 早い。下の限界）とは窓の数え方が違う。
  - 実制作で使った分離ボーカルは手元に無いので、実曲では確かめていない。
- 実制作の台本の、50 ms ごとの音量を記号で並べる表示（`env`）は移していない（`voice` の区間で足りる）。歌詞の行から LRC を書くのは
  `mv export subtitles`（終わりの印の付け方は台本と違う）。

## 限界

- **明滅の測定（`mv gate flashes`）は、画面全体の平均の明るさだけを見る。**
  - 画面の一部だけの明滅は測れない（全体の平均に薄まる。目安にある「画面のどれだけの広さが光るか」は見ていない）。
  - 色（赤）の明滅は測らない。
  - 暗い側の明るさの条件は見ていない（目安には、暗い方の状態が一定より暗いときだけ数える条件がある。ここでは明るい場面どうしの変化も同じに数える）。
  - 規格への適合を判定するものではない。回数が上限以下でも、基準への適合や安全の確認にはならない（判定は別の道具と人の役目）。
  - 測り方の細部: コマを縮めてから線形に戻すので、画素ごとの細かい明暗が強い絵では明るさが少しずれる（1080p の合成の雑音の絵で、縮めずに測った値との差は最大 0.03）。コマの間隔が一定でない動画は、基準のフレームレート（ffmpeg の見積もり `tbr`）に揃えて測るので、その見積もりが実際のいちばん短い間隔より粗いと、落ちるコマがある（平均と基準が小数 2 桁まで同じ動画は、一定として扱う）。BT.709 でない行列で書いた動画は、色の濃い所の明るさがずれる（BT.601 として読むと、赤の 0.21 が 0.17）。
- **歌い出しの推定は正解より約 20 ms 早い**（2026-11-08 に `mv gate demo` の素材で測定）。補正は入れない（2026-11-11 にユウが決めた。実曲では測っていないので、合成の素材の値で直すと推定を実測扱いすることになる）。音量の包絡は 30 ms の窓を 10 ms 刻みで前向きに取るので、窓が歌い出しに掛かり始める 2 刻み前から上がり始め、谷から上がり始めた最初の点へ戻す式がそこを選ぶ。立ち上がりの長さにはほぼよらず、背景の床が高いときだけ上がり幅のしきい値を越える点が遅れて偏りが小さくなる。実曲（子音・残響つき）では未測定。

  | 立ち上がり | 背景の床（音の山に対して） | 行ごとの差（推定 − 正解, ms。4 行） | 平均 |
  |---|---|---|---|
  | 5 ms | −60 / −40 / −25 dB | −20, −20, −20, −20（どの床でも同じ） | −20 |
  | 30 ms | −60 / −40 dB | −20, −20, −20, −20 | −20 |
  | 30 ms | −25 dB | −10, −10, −10, −10 | −10 |
  | 80 ms | −60 / −40 dB | −20, −20, −20, −20 | −20 |
  | 80 ms | −25 dB | 0, 0, 0, 0 | 0 |

  4 行とも `vocals_onset` で見つかり、行ごとのばらつきは無い（素材が同じ形の音だから）。gate の許容は 0〜0.2 秒なので、宣言した時刻が正解のちょうど 0 秒前の行は、この偏りで不合格側に出る。
- 顔の枠は人が書く（多くは目測の推定）。`mv gate faces` は枠を写して数えるだけで、顔を見つけない。枠が実際の顔より小さいと、見切れを見落とす。
- 「重ねの字と顔」は、重ねる前の層のアルファだけを数える（仕上げで広がる影・光彩・後光や、土台の絵に描いてある字は数えない）。枠の外に近い字との距離は測らない。
- 揺れの位置の列・骨格は別途用意する（推定の道具は持っていない）。無ければその検査は未実施になる。顔は `"faces": "auto"` で粗く推定できるが、正面を向いた 1 人の全身を前提にした頭の帯で、顔の検出ではない。
- 入力の `timeline.json` は `mv dance render` の出力か、同じ形式で書いたもの。
- 書き出しの表（`mv gate final`）は、渡した報告を読むだけで、`check.video_frames` を自分では回さない。最後のコマの明るさは、画面全体の平均だけを見る（暗い場面で終わる動画は `--min-last-mean` を下げる）。

## 実素材確認（2026-11-27）

- **`mv gate timeline`**: `mv export remotion-props`（32 秒・30 fps・7 行）と本物の Remotion 4.0.532 で描画した実 960 コマ RGBA PNG 連番を入力し、行ごとの `--frames DIR:<line_id>` で全 7 行の可視開始・終了フレーム（`[18, 119]`・`[131, 226]`・`[243, 407]`・`[474, 565]`・`[565, 692]`・`[692, 789]`・`[792, 924]`、`unseen_lines: 0`、props との差 0 コマ）と下帯の箱（`y = 0.846〜0.899`）を計測し、出力 `timeline.json` をそのまま `mv gate check` へ接続して合格（`overall: pass_with_skips`・終了コード 0）することを確認した。なお、複数行が同一位置を共有する単一連番へ同じ `--hints` 箱を渡した場合は連続可視として扱われ、`mv gate check` が「字の重なり」として検出することも実確認した。
- **`mv gate flashes`**: 31 秒の実完成ダンス MV へ既定の `delta: 0.10` と `--delta 0.08` で実行し、両条件で明滅 4 件・`status: pass` と報告された。独立した計数との照合や、用途別のしきい値の確認が残るため、実験的を維持する。
- **`mv gate voice`**: 実分離ボーカル（Demucs の FLAC ステム）の 0〜60 秒から声候補を 7 区間（8.80 秒以降）抽出した。独立計算した生ステム RMS は無音イントロ（0.5〜8.0 秒）が `−89.29 dB`、抽出区間の平均が `−36.41 dB`（最小 `−50.86 dB`）で、平均との差は 52.9 dB だった。各区間の境界・誤検出・見逃しの試聴による確認は未記録。

- **`mv gate check`・`mv gate lines`**: 実プロジェクトのダンス run に対する `mv gate check`（終了コード 0・`pass_with_skips`）および実音源での `mv gate lines`（7 行中 `vocals_onset` 4 件・`not_found` 3 件、`lines_measured.json`・`lines_table.csv` 出力）の実行を確認した。人の試聴で確定した歌唱時刻との照合運用が残るため、これら 2 コマンドは引き続き実験的とする。
