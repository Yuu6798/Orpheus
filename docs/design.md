# MV制作パイプライン リポジトリ実装設計 v0.1

作成日：2026-10-02（JST）

## 1. 決定事項と初回の完成形

新規リポジトリ `ugh-mv-pipeline` に、既存ツールを呼ぶ実行層、工程間のJSON契約、MV用の演出テンプレートを置く。Sitesは初期実装に含めず、確認にはRemotion Studioを使う。既存のVoiceGenesisや作曲エンジンの中核は変更しない。

初回はユーザーが指定する楽曲の30〜60秒、16:9、1920×1080、30fps、ステレオ音声のMP4を完成させる。これはPoCの初期設定であり、全作品への固定条件ではない。静止画のパン・ズーム・フェード、歌詞表示、拍に合わせた切替を扱う。キャラクターが演技する生成動画、口パク、汎用編集アプリは対象外。これらは初回MV完成後に必要に応じて追加する。

作品の音は元の完成ミックスを使う。分離ボーカルは歌詞同期用、完成ミックスは拍・構成解析と最終映像用とする。利用できる元ステムがあれば分離を省略する。

添付の「作曲デフォルトフロー v1.2」の、制作→実測→聴取・確認という順序を引き継ぐ。歌詞同期研究や自動採点器の完成を待って映像制作を止めない。

## 2. 流用方針

| 工程 | 初期方針 | 採用状態と留意点 |
| --- | --- | --- |
| 音声の変換・メタデータ | FFmpeg / ffprobe | 既存CLIを呼ぶ。独自エンコーダーは作らない |
| ボーカル分離 | 既存HTDemucs経路を探索・接続。なければAudio Separatorを候補にする | 既存経路の場所・版・起動方法は本設計では未確認。分離モデルの再開発はしない |
| 拍・音量 | librosa | 基本経路。サビという意味ラベルまでlibrosa単体に保証させない |
| 曲構成 | allin1を任意アダプターとして試す | BPM・拍・小節頭・構成ラベルのJSON出力あり[1]。導入に支障があればlibrosa＋手動区間を使う |
| 歌詞同期 | Qwen3-ForcedAlignerを最初の比較候補。必要に応じてWhisperX等と比較 | Qwenは日本語対応だが整列モデルの対象はSpeechで、歌唱精度は未検証[2]。既存の動作済み経路がある場合はそれを先に使う |
| 同期の予備候補 | stable-ts、syncalong、SOFA | stable-tsは開発休止[3]。syncalongはASR後の照合と補間を含む[4]。SOFAは歌唱向けだがモデル・辞書の適合確認が必要[5] |
| 演出案 | Claudeへのファイル受け渡し | 初期は人がJSONを搬入する。常駐BotやAI間の直接通信は必須にしない |
| 画像 | GPT画像生成、または既存画像の取り込み | 手動搬入を初期から用意。無人API接続は利用環境・予算の設定後に追加 |
| 映像 | Remotion公式テンプレート・部品・公式Agent Skills | 映像コード作成、Studio確認、描画に流用[6][7] |
| 字幕 | @remotion/captionsへの変換 | 正典の歌詞データから変換し、字幕用の別の正解歌詞を作らない[8] |

候補を全て導入しない。既存の動作経路を優先し、同期比較も初回は最大2経路に限定する。どちらも不十分なら手修正して映像制作を続け、問題区間だけを後で改善する。

SaaSとの完成映像比較は任意の別実験。初期依存にしない。有料テンプレート、画像API、クラウド計算には費用があり得る。具体的な課金額は実装時に使用モデル・版・枚数で確認する。Remotionの利用条件は導入版のライセンスを記録し、Editor Starterの料金・条件とは分ける[9]。

## 3. 役割と実行環境

| 担当 | 責任 | 成果物 |
| --- | --- | --- |
| Codex | アダプター、契約検証、共通Remotion実装、描画、再実行 | 実行コード、ログ、動画 |
| Claude | 曲・歌詞に対応した構成、画面設計、カット、動きの指定 | storyboard.json、演出意図 |
| GPT画像生成 | 基準画像と参照付きのシーン画像 | images、assets.json |
| ユーザー | 世界観、同期、視聴品質の最終判断 | 修正指示、採否 |

Claudeが特殊演出のコード案を作る場合も、共通実装への統合責任はCodexに置く。通常はJSON内の既定プリセットを使う。

想定環境はローカルPCのPython、Node.js、FFmpeg。Pythonはuv、Nodeはpnpm等のロックファイルで再現性を保つ。具体的な版は依存関係の初回導入試験後に固定し、latestを常用しない。モデルが環境競合を起こす場合だけ、別venvのCLIとして切り離す。Dockerや常駐サーバーは初期必須にしない。

ローカルGPUは主に分離・同期モデルに使う。Remotionの全工程がGPUで高速化されるとは前提にしない。PC停止中はローカルのジョブは進まない。

## 4. リポジトリ構成

以下は実装時に作る構成。今回の納品は設計書・契約・架空データのみ。

```text
ugh-mv-pipeline/
  README.md
  AGENTS.md
  pyproject.toml
  uv.lock
  package.json
  pnpm-lock.yaml
  .env.example
  contracts/                 # JSON Schemaの唯一の正典
  src/mv_pipeline/
    cli.py                   # 工程別の起動
    runner.py                # 状態・キャッシュ・再開
    adapters/                # 分離・同期・構成・画像の薄い接続
    normalize.py             # ツール固有形式を共通形式へ変換
    validate.py              # JSON＋意味的整合性
  renderer/
    src/                     # Remotionの共通コンポジション
    presets/                 # 静止画、歌詞、フェード等
  prompts/
    storyboard.md            # Claudeへ渡す指示
    image_style.md           # 基準画像・一貫性の指示
  docs/
    design.md
    runbook.md
  tests/                     # 契約、再開、最小描画
  examples/                  # 小さな架空の契約例
  projects/                  # 楽曲素材・実行結果。原則Git対象外
```

楽曲ごとの作業領域には `inputs/`、`work/`、`edits/`、`runs/<run_id>/` を置く。元音源と原歌詞はinputsで保持し、workに正規化音源、分離ステム、rawの解析結果を保存する。editsには手修正した時刻や区間を残す。runには使用したJSONのスナップショット、画像一覧、ログ、出力動画を保存する。

Gitへ入れるのはコード、スキーマ、プロンプト、ロック、再現用の小さな例。音源、画像、モデル重み、API鍵、大きなログ、MP4は入れない。成果物は既存の楽曲資産保存先へ保存先指定で搬出できるようにし、初期は手動コピーで足りる。Driveアップロードや公開は独立の工程とする。

AGENTS.mdには「動く既存ツールを優先」「入出力契約を無断変更しない」「推定を実測扱いしない」「制作を採点器開発で止めない」「依頼のない送信・公開をしない」を記載する。

## 5. 処理の流れ

1. **入力を固定する**：音源、歌詞、対象区間、fps、画面サイズを読む。元ファイルのSHA-256を保存する。
2. **時間軸を統一する**：1回だけPCM WAVへ変換し、指定区間を切り出す。以降の時刻は切り出し音源の先頭を0秒とする。元曲上の開始秒は別フィールドに残す。
3. **解析する**：完成ミックスから拍・音量・構成候補、ボーカルから歌詞時刻を得る。どちらも同じ音源原点へ戻してanalysis.jsonへ正規化する。モデル用のリサンプリングで原点を変えない。
4. **確認・修正する**：手修正を別ファイルで記録してanalysis.jsonへ適用する。再解析で手修正を消さない。入力変更で修正が適用できない場合は未解決として示す。
5. **演出を作る**：Claudeへanalysis.json、歌詞、ユーザーの世界観、スキーマを渡し、storyboard.jsonを得る。推定構成を根拠に使っても確定事実として書き換えない。
6. **画像を用意する**：基準画像を1枚確定し、各シーンの画像生成・編集で参照する。既存画像も同じassets契約で受け入れる。
7. **描画する**：storyboard・assets・音源から共通Remotionコンポジションを組み立てる。字幕データはanalysisから作る。プレビューと本番で同じコンポジションを使用する。
8. **検証・視聴する**：ファイルと時間軸の機械検査を行い、人が同期と映像品質を確認する。技術的成功と作品採用を分けて記録する。

音源に遅延を加える分離器や前処理はオフセットを記録し、同期時刻を補正する。既知の遅延が補正できなければ手確認対象とする。元音源が更新された場合、旧解析の自動流用を禁止する。

## 6. JSON契約

同梱のcontractsを仕様の正典とする。数値例・歌詞例は架空。スキーマで表せない参照整合性はvalidate.pyが検査する。

### analysis.json

- `schema_version`、`analysis_id`、音源の相対パス・SHA-256・サンプルレート・サンプル数・尺・元曲からの開始位置。
- `bpm`、拍時刻、構成区間。取れていないBPMはnull、拍や区間は空配列にできる。
- 歌詞は `id / text / alignment_text / start_s / end_s / timing_source / review_status`。表示歌詞と同期用の読みを分けられる。
- `timing_source` は `model / interpolated / manual / unknown`。時刻が取れない場合はstart/endともnullにし、無理に埋めない。
- `confidence` はツールが意味を定義して出す場合のみ保存。取れないときはnull。異なるツールのスコアをそのまま比較しない。
- 使用ツール名・固定版・モデル名、未解決事項を残す。

### storyboard.json

- 共通ヘッダー、`analysis_id`、解析ファイルのハッシュ、音源ハッシュで入力を特定する。
- `render`に整数fps、幅、高さ、総フレーム数を置く。v0.1は整数fpsに限定する。
- 各シーンは `id / start_frame / end_frame / lyric_ids / asset_id / prompt / motion / transition_in / intent`。
- 範囲は半開区間 `[start_frame, end_frame)`。全体で0から総フレームまでを隙間なく覆う。時刻ではなく整数フレームを描画の正典にする。
- `motion` は初期に `still / slow_push / pan_left / pan_right`。任意のコードやシェルをJSONへ入れない。
- `transition_in` は `cut / crossfade` とフレーム数。v0.1のクロスフェードはシーンの冒頭で前シーンの最終画像を重ね、総尺を短縮しない。
- 字幕はanalysisの歌詞時刻から描画し、シーン変更で途中の歌詞が消えないよう全体レイヤーに置く。lyric_idsは演出上の関連参照であり字幕時刻を上書きしない。

### assets.json

- 各画像の `asset_id / path / sha256 / width / height / source / prompt / reference_asset_ids`。
- `source`はgeneratedまたはimported。生成した場合は利用できるモデル名・生成条件も保存する。
- 基準画像も通常のassetとして登録する。参照画像のハッシュ変更は依存画像の再確認対象とする。
- JSONにAPI鍵や期限付きのダウンロードURLを残さない。パスはプロジェクト起点の相対パスで、外への遡りを禁止する。

### 時間・参照の意味的検査

音源の `duration_s = sample_count / sample_rate` を基準とする。総フレーム数は `ceil(duration_s × fps)`。出力時の末尾パディングは最大1フレーム未満とし、歌の途中を落とさない。

時刻→フレームは開始をfloor、終了をceilで変換し、全体範囲内へ制限する。隣接字幕が境界1フレームだけ重なる場合は次の開始を優先して調整する。元から歌唱が重なる場合は別問題として明示し、初版では人が表示行を選ぶ。

検査項目はIDの一意性、参照IDの存在、ハッシュ一致、時刻の範囲、開始＜終了、シーン連続性、未知プリセット、画像ファイルの存在・読込可否、絶対パス／パストラバーサルの拒否。拍は厳密昇順とする。

歌詞時刻がunknownまたは未解決なら通常の字幕付き本番出力を止める。手修正または明示した歌詞非表示で先へ進める。確認用プレビューは未確認であることをログへ記録して許可する。

## 7. 実行・再開・課金

下記は実装予定のCLIであり、現時点で動くコマンドではない。

```bash
uv run mv init projects/song-a --audio song.wav --lyrics lyrics.txt --start 60 --duration 45
uv run mv analyze projects/song-a
uv run mv export-brief projects/song-a
uv run mv import-storyboard projects/song-a storyboard.json
uv run mv import-assets projects/song-a assets.json
uv run mv preview projects/song-a
uv run mv render projects/song-a --profile final
uv run mv verify projects/song-a
uv run mv resume projects/song-a
```

runnerはPythonからCLIを引数配列で起動し、shell文字列を組み立てない。初期は1プロジェクト1プロセスの逐次実行とし、ロックファイルで二重起動を防ぐ。キューサービス・DB・分散実行は導入しない。

job.jsonは `job_id / input_hashes / stages / current_run_id` を保持し、各stageは `pending / running / waiting_input / succeeded / failed / stale` を持つ。開始・終了時刻、出力ハッシュ、終了コード、短いエラーを記録する。tmpへ書いてatomic renameで確定し、成功ファイルを途中出力で上書きしない。異常終了後はrunningを再検査し、出力が検証できた工程だけ復旧する。

キャッシュキーは工程名、入力ハッシュ、設定、ツール・モデル版の組合せ。演出はプロンプト・スキーマ版も含める。下流が依存する入力の変更でstaleにする。

| 変更 | やり直す範囲 |
| --- | --- |
| 音源・対象区間 | 解析・同期以降。既存画像は適合性を確認して再利用可能 |
| 歌詞 | 同期、演出の関連部分、字幕、描画 |
| 手修正時刻 | 演出の該当区間を確認、字幕・描画。音源分離は再実行しない |
| 画像1枚 | その画像の再登録・全体描画。初版は部分動画キャッシュを作らない |
| 動き・文字色 | 描画のみ |

API画像生成は枚数・設定・予算上限をまとめた計画を作り、ユーザーが承認した範囲を記録する。承認済み範囲は繰り返し確認しない。予算未設定の自動大量生成は開始しない。自動再試行は費用が重複しないと確認できる場合のみ。タイムアウトなどで生成結果が不明ならwaiting_inputとして照会・回収し、盲目的に再生成しない。初期の手動画像搬入ではこの課金制御は不要。

Drive通信基盤のid/status/reply_toは外部通信を導入する段階で対応付ける。初版のファイル連携に返信プロトコルを持ち込まない。

## 8. 検証と完成条件

### 機械検査

- JSON Schemaと意味的整合性が通る。
- MP4を最後まで復号でき、映像・音声ストリーム、解像度、fps、尺が設定と一致する。
- 合意した原点から音声を配置し、映像尺との差は1フレーム＋音声エンコーダー由来の許容範囲以内。具体的な許容値はffprobeの実出力に合わせて記録する。
- 必要画像の欠落、歌詞の範囲外時刻、シーンの隙間を検出する。暗い演出や静かな曲を一律に異常と判定しない。
- 音声欠落・不意の無音は元音源との区間比較で確認する。圧縮後のPCM完全一致を要求しない。

### 視聴確認

歌詞行の開始・終了、繰り返しサビ、長く伸びる母音、英日混在箇所を確認する。初回の同期比較は同じ30〜60秒と人が付けた境界を用い、時刻誤差、行の欠落、必要な手修正数を記録する。字幕として許容できるかを優先し、未確認の数値を精度として報告しない。

画風・人物・衣装の連続性、切替の気持ちよさ、文字の可読性、サビの展開を人が見る。画像埋め込み類似度やLLM点数だけで採用を決めない。

技術検査が通った状態をtechnical_pass、ユーザーが作品として採用した状態をacceptedとして分ける。初期は短いチェックリストと指摘時刻だけでよい。

### 必要なテスト

1. 契約と意味検査：入力ハッシュ不一致、存在しない画像、シーンの隙間、補間／不明時刻を検出できる。
2. 再開：描画だけ失敗した場合に分離・API生成を再実行しない。
3. 5〜10秒の描画：静止画・字幕・音声が実際のMP4へ出る。

初回PoCの完了条件は、指定曲の30〜60秒MVが再実行できる、画像1枚と歌詞時刻1箇所の差し替えができる、入力と使用版と修正履歴が残る、視聴指摘に対し1回修正版を出せること。全候補モデルの比較完了は条件にしない。

## 9. 実装順

| 段階 | 作るもの | 到達条件 |
| --- | --- | --- |
| 0 | 既存経路・GPU・FFmpeg・Remotion利用条件の確認、依存版の固定 | 小さな実行確認ができる |
| 1 | 契約読込、既存画像＋手修正歌詞時刻＋音源のRemotion描画 | 5〜10秒のMP4が出る |
| 2 | 正規化・HTDemucs接続・librosa、必要ならallin1 | 同一時間軸のanalysis.jsonができる |
| 3 | 歌詞同期アダプター、修正の保持 | 自動結果を確認・修正して描画できる |
| 4 | Claudeへのbrief出力・storyboard搬入、GPT画像の参照管理 | 指定曲30〜60秒のMVを完成 |
| 5 | stale判定・resume・検証結果・runbook | 差分修正を再実行できる |

最小限の入力識別・安全な出力保存は段階1から入れる。汎用的な再開管理は段階5で整える。次段階に先立つ大規模な管理基盤は作らない。

その後の拡張は、フル尺、複数比率、API自動生成、ローカル実行ジョブを扱うSites画面、クラウドワーカーの順で必要なものだけ選ぶ。Sitesを追加しても契約とrendererは変更せず、受付・進捗・確認の役割を与える。ローカルワーカーとの接続認証とジョブ受取方式はその時点で設計する。

## 10. 未確定事項と実装への引継ぎ

未確定なのは対象音源・正しい歌詞・切出し区間、既存HTDemucs経路、PCのGPU/VRAM、画像生成の実行方法と予算。これらは実音源で制作を始める際に確認する。設計書の作成や最小描画経路の実装を妨げない。

本納品ではJSONの例とスキーマの一致を確認する。外部ツールの導入、実音源による同期精度、Remotion描画、API動作は未検証。下記資料の機能記述と本プロジェクトでの動作実績を区別する。
