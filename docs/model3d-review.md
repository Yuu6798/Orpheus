このページは初回監査と PR #24 の記録に、Windows の PC での確認と面領域の追加（下記）を足したもの。後続の既存制作 worker 接続は
[model3d の3Dダンス工程](model3d-dance.md)を参照。以下の「未接続」は初回監査時点の状態を示す。

部品の加工・検査・OBJ 出力をレシピと記録で動かす基盤は実動作した。設定画からリグ付きキャラクターを作り、
実キャラの 3D ダンスまで出力する一連の機能は、この実装にはまだ接続されていない。
設計 v0.5 の段階では M0〜M1 の土台であり、r6 の再実行を含む M1 完了には達していない。

## この変更で扱う指摘

| 指摘 | 修正・確認する挙動 |
|---|---|
| 未確認の役割で成功し、成功キャッシュにも載る | 使用する未確認の役割は needs_review / unresolved に残し、その工程を再利用しない。無関係な対応は警告のみ |
| 35 頂点へ結合後も 42 頂点用リグの単体検査だけが通る | weld の正確な旧→新頂点対応でウェイトを移し、加工後メッシュの頂点数・topology と照合する |
| Blender 観測が world / pose を名乗りながら rest-local の骨を返す | 対応する rest だけを受け付け、局所座標と matrix_world の意味を明示する |
| Blender の Python 例外が終了コードに反映されない可能性 | Python 例外の非ゼロ終了コードを起動引数で指定する |
| TripoSR の重み不一致や原本比較の不合格でも終了コード 0 | 固定条件を実測確認し、不一致・比較不合格を非ゼロ終了にする |

これらの回帰検証は合成素材・純粋関数・代役プロセスを使う。本物の Blender 起動、TripoSR 推論、
リギング、実キャラの描画をこの変更で新たに実証したとは扱わない。
現在の合成デモも、実キャラの描写品質やアニメ付き出力の完成を保証しない。

修正後の同じ環境で `uv run pytest -q -ra` は **785 passed / 1 skipped**。skip は上記と同じ比較基準の不足。
`pnpm typecheck` と `pnpm test`（2 件）も通過した。修正後のデモは 9 工程 succeeded、貫通 15→0、
加工後メッシュと移し替え後ウェイトはともに 35 頂点で topology も一致した。設定画の代役レシピは needs_review を維持する。
この件数はローカル実行の記録であり、CI や実キャラの描写品質の判定ではない。

## Windows の PC での確認（2026-11-03）

変更前の値は commit `de58957`（main）、変更後の値は面領域の変更（下記）を PR #25 を含む main（`7e9801b`）の上に載せたもの。
Windows 11 Home（スマート アプリ コントロールはオン）・署名つき Python 3.13.17・uv 0.13.5、
`uv sync --locked --extra analysis --extra fx --extra model3d` の環境で確認した。この PC には Node が無く、`pnpm` の検査は実行していない。

| 確認 | 実測 | 範囲 |
|---|---|---|
| Python テスト（変更前） | 783 passed / 2 failed / 1 skipped | 失敗の 2 件は Blender の代役をシバン付きのスクリプトとして直接起動するテストで、Windows では起動できない（WinError 193）。skip は POSIX 専用のプロセスグループの検査 |
| Python テスト（変更後） | 819 passed / 1 skipped（面領域の 12 件を含む） | Blender の代役は Windows では python を呼ぶ `.cmd` にした（本物の Blender の起動ではない）。PR #25 で入った dance-recipe のテスト 3 件も、シンボリックリンクを作る権限（WinError 1314）とシバン付きの代役（WinError 193）を前提にしていて Windows では落ちていたので、代役を同じ方法にし、リンクを作れない環境では照合済みのコピーを確かめるようにした。skip は上と同じ |
| 合成デモ・設定画の代役レシピ | 9 工程 succeeded（結合 42→35 頂点、貫通 15→0）／ needs_review（8 頂点・12 三角形の閉じた箱） | Linux の記録と同じ値。代役の生成器で、画像条件付きの推論ではない |
| 本物の TripoSR | 未実施 | 生成器の手順は Linux 前提（gcc/g++ で torchmcubes の C++ 拡張をビルド、Python 3.12）。この PC には WSL もコンパイラも無く、Python は 3.13 だけ。スマート アプリ コントロールは評判の無い未署名の DLL を止めるので、その場でビルドした拡張は読み込めない見込み（推定・未試行） |

### 面領域を実メッシュに結び付けた結果

2026-11-03 の検証記録にある初期モデル（実キャラの正面設定画 1 枚から TripoSR で生成。8,518 頂点・16,952 三角形・15 連結成分・
閉じていない・頂点色あり・topology `1f258e2b…`）を、この変更の CLI で扱った。素材はリポジトリの外（`projects/`）に置いた。

| 確認 | 実測 |
|---|---|
| 連結成分 | 成分 0 が 16,468 面・8,247 頂点（境界辺 68 で閉じていない）。残り 14 成分は 8〜76 面の小さな塊（13 個は閉じ、1 個は境界辺 4）で、胴の前側の高さ（正規化座標 z = +0.07〜+0.21）に集まる |
| 面領域 | 成分 0 を `body`、成分 1〜14 を `x.fragment` に当てた（どちらも `inferred`・`unconfirmed`。役割は大きさと位置から置いた候補で、人の確認前）。16,952 面すべてが重なりなく当たり、`semantic check` は全部 `bound` |
| 正規化の後の選択 | `mesh.transform`（×1.6592。高さ 1.70 m への未校正の初期合わせ）の後も頂点構成は同じで、`select` がそのまま当たった。`body` の切り出しは 1 成分・境界辺 68、`x.fragment` は 14 成分。面領域が未確認なので run は `needs_review` |
| 古い対応と付け替え | 距離 1e-6 の結合でも 19 組の頂点がまとまり、退化した 6 面が消えた（8,518→8,497 頂点、16,952→16,946 面）。結合後のメッシュには 2 つの面領域とも `stale` で、`select` の工程は止まる。結合の面の対応で付け替えると、`body` は 6 面を失って 16,462 面（`unconfirmed` のまま）、`x.fragment` は 484 面のままで、どちらも `bound` に戻った |

髪・顔・衣装は成分 0 の中でつながっていて、連結成分では分けられない。分けるには、面を人が選ぶ（Blender で選んだ面番号を
`--faces`、重心の箱を `--box`）か、形状修正の工程で分離する。自動の部位分割は実装していない。

| 項目 | 現在 | 次に必要な実装・確認 |
|---|---|---|
| 意味役割と部位選択 | 面領域を頂点構成に結び付けて持ち、工程の `select` で役割の面だけを加工する。古い対応は検出して止め、結合の正確な面の対応で付け替える（上記「Windows の PC での確認」） | 実メッシュの部位の面を人が分けて確認する（自動の部位分割は無い）。リトポロジーなど正確な対応の無い変更の後の対応の作り直し |

別試作の成功とこのリポジトリの実行結果は合算しない。素材・モデル・重み・動画は Git に置かず、成果物と制作記録で接続する。

接続した（[model3d の3Dダンス工程](model3d-dance.md)）。次の順番は、実キャラの部位の面の確認、本物の TripoSR のこの実装からの再実行
